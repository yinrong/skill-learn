## 2. 规划

### 2.1 当前瓶颈分析

### 1.1 基准数据

| 条件 | F1 | 说明 |
|------|-----|------|
| Claude-sonnet-4.6 + Skill | **0.232** | 目标上界 |
| Qwen3-14B + Skill | 0.109 | 基座有 Skill 时的表现 |
| Qwen3-14B SFT N2-6ep 无 Skill | 0.119 | 当前最佳，**目标的 51%** |

当前距目标约差 0.113 F1，需提升约 **2×**。

### 1.2 已识别的瓶颈

| 类别 | 问题 | 影响 |
|------|------|------|
| 数据质量 | 训练样本由规则引擎模板生成，输出格式单一、推理链机械 | 模型学到模板，泛化弱 |
| 数据格式 | N2~N4 模型无 Skill 时输出中文格式（第1条/规则②），而非 rule1 | F1 被低估；格式 drift 影响提取 |
| 规则覆盖 | N2 以 rule1 为主（recall=0.675），rule3~8 recall=0.000 | 模式崩塌，只会检 1~2 条规则 |
| 训练方法 | 纯 SFT，无正确/错误反馈信号 | 无法纠正系统性漏报和误报 |
| 模型容量 | 当前基座规模有限；8B 预训练 SPC 知识更弱 | 更大模型可能更容易内化 |

## 2.2 提升方向（按预期收益排序）

### 方向 A：Claude 作为教师生成高质量数据（最高优先级）

**核心思路**：用 Claude-sonnet-4.6 替代规则引擎模板生成训练样本。Claude 本身有 SPC 知识、能写出高质量推理链，生成的输出多样性远超模板。

**执行方式**：
- 给 Claude 发送测试集格式的输入（25 点数据 + USL/LSL），加 Skill 文档
- Claude 输出完整分析（含 `<think>` 推理链，含 rule1~rule8 逐条检查，含 CPK 计算，含 3 条处置建议）
- 对 Claude 输出用规则引擎验证正确性（violations 和 CPK），过滤错误样本
- 保留验证通过的样本作为训练数据

**优势**：
- 推理链质量高（逐条分析、边界说明、计算过程完整）
- 输出格式统一（可在 prompt 中要求英文 rule1 标识符）
- 自然多样性（措辞、侧重点、分析深度各异）

**预期规模**：500~2000 条（Claude API 调用成本可控）

**与 route2.1 数据的区别**：

| | route2.1（模板） | route2.1.1（Claude 教师） |
|--|----------------|--------------------------|
| 推理链 | 机械模板，格式固定 | 自然语言，多样化 |
| 错误率 | ~2%（自验证） | ~5~10%（需规则引擎过滤） |
| 多样性 | 低（同一模板） | 高（Claude 自由发挥） |
| 成本 | 极低 | 中等（API 费用） |

---

### 方向 B：格式统一（快速修复，立即执行）

**核心思路**：在数据生成阶段强制要求输出英文 `rule1`/`rule2` 标识符，消除中文 format drift。

**执行方式**：
- Skill 文档 + system prompt 中明确要求："违规规则必须写作 rule1、rule2...rule8（英文小写，不用中文）"
- 同时修改 generator.py 模板，output 字段统一使用 `rule1` 而非 `第1条`
- 重新生成 N1~N4 数据，重新训练，重新评测

**预期收益**：消除评测时的格式提取误差，N2~N4 的真实 F1 可能比当前高。

---

### 方向 C：RL 强化训练（GRPO，中期方向）

**核心思路**：SPC 规则检测是**可验证任务**（有确定性规则引擎作为评判），天然适合强化学习：
- 奖励信号：规则引擎评判模型输出的 violations 列表是否与 ground truth 一致（F1 作为 reward）
- CPK 奖励：|pred_cpk - gt_cpk| < 0.1 则加分
- 格式奖励：输出包含 `rule1`~`rule8` 英文标识符则加分

**方法选择**：GRPO（Group Relative Policy Optimization）

| 方法 | 适用场景 | 优势 |
|------|---------|------|
| SFT | 有高质量示范数据 | 快速、稳定 |
| DPO | 有偏好对（好/差） | 直接对齐偏好 |
| **GRPO** | 有可验证奖励函数 | 无需人工标注，奖励来自规则引擎 |
| PPO | 复杂奖励环境 | 效果强但实现复杂 |

**GRPO 执行流程**：
```
1. SFT 初始化（先用方向 A/B 的数据做 SFT）
2. 对每个输入采样 G 个输出（G=8）
3. 规则引擎计算每个输出的 F1 score 作为 reward
4. GRPO 更新：鼓励高 reward 输出，抑制低 reward 输出
5. 迭代直到收敛
```

**工具**：LLaMA-Factory 支持 GRPO（`finetuning_type: grpo`）

## 2.6 Claude 作为教师的具体分工

| 角色 | Claude-sonnet-4.6 承担 | 规则引擎承担 |
|------|----------------------|------------|
| 数据生成 | 生成推理链 + 自然语言输出 | 生成 ground truth violations + CPK |
| 质量过滤 | — | 验证 Claude 输出的正确性（F1>0.8 保留） |
| 难例生成 | 生成边界条件样本（如恰好触发/恰好不触发） | 验证边界判断是否正确 |
| 格式示范 | 示范"完整分析"的风格 | — |
| 评测上界 | Claude+Skill F1=0.232 是追赶目标 | — |

Claude 的优势在于推理链质量，规则引擎的优势在于判断准确性——两者结合生成高质量训练数据。
