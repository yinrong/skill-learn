# route2.1.1 Skill 内化效果提升计划 — 目标与约束

> 版本：v2（2026-04-27，含对话补充要求）  
> 前置：route2.1 Demo 完成，当前最佳 F1=0.119（N2-6ep，无 Skill）  
> 目标：F1 接近 Claude-sonnet-4.6+Skill 水平（F1≈0.232），推理快、资源少

---

## 1. 目标

### 1.1 目标

**总目标**（三项，缺一不可）：
1. SKILL 内化模型达到 Claude-sonnet-4.6+Skill 的能力，且推理更快、资源消耗更少
2. 探索全部可能提升效果的方法，形成《SKILL 内化方法》文档
3. 达到目标分 **5 个阶段**执行；每个阶段结束后，根据过程与阶段结果重新规划，按照最初目标调整计划，以期达到更好的效果

- **进入 route2.2 的条件**：任意模型 rule_f1 ≥ 0.18 且 per_rule recall 全部非零

**必须探索的维度**：
- 训练框架（不限于某一种）
- 模型名称与参数量（不同系列、不同规模）
- 微调参数（rank、epoch、学习率、数据配比等）
- 量化水平（bf16、fp16、int8、int4/QLoRA 等）
- 8 卡（8× H20 96GB）能支持的最大参数量（LoRA 与 QLoRA 两种模式）

**结果中必须包含的指标**：

| 指标 | 说明 |
|------|------|
| 模型通用能力退化率 | SFT 后模型在通用任务上能力相对基座的下降程度 |
| 训练时间 / 卡数 | 完成一次完整训练所需的挂钟时间及占用 GPU 数量 |
| 推理时间 / 卡数 | 对 200 条测试集完成推理的总时间及占用 GPU 数量（单样本均值） |

**综合得分公式**：

```
综合得分 = 任务得分 × (1 - 通用能力退化率) / (推理时间_s × 推理卡数 × 单卡显存_GB) × 1000
```

- **任务得分**：当前以 rule_detection_f1 作为占位指标；F1 是否是衡量 SKILL 内化效果的最佳指标，本身是待探索问题，可随阶段重规划替换
- **通用能力退化率**：SFT 后模型在通用 benchmark（如 MMLU、GSM8K）上相对基座的得分下降比例；退化率越低越好
- **推理时间_s**：单样本推理均值（秒）
- **推理卡数**：推理部署所占用的 GPU 数量
- **单卡显存_GB**：推理所需单卡显存峰值

### 1.2 执行约束

**执行方式**：
- **开放式探索**：真实微调迭代，穷尽所有可行方法，或累计工作达 **60 小时**为止
- **必须启用 Agent Team 并发执行任务**，不得单线程串行推进
- 必须最大化 GPU 并行利用率，所有可用 GPU 同时承载不同实验

**过程记录**：
- **必须保留执行日志**（每个训练/评测任务写日志文件）
- **阶段性总结和再规划**：每完成一个批次后写总结，分析结果，重新规划下一批
- `progress.md` 必须在每批次结束后（或至少每 6 小时）更新
- **所有要求输出的文件，必须在执行目录实时维护 `index.md`**：每产出一个新文件（日志、结果 JSON、checkpoint、报告等）立即更新 `index.md` 中对应的链接，执行过程中保持实时可查

**GPU 监控**：
- **必须每 15 分钟检查一次 GPU 利用率**
- 若发现 GPU 空闲，必须反思：规划时是否没有正确安排并发？
- 若是并发规划失误导致空闲，**必须立即重新规划**并补充任务

**语言要求**：
- 所有结果、过程、总结文档**必须用中文写**

## 2. 引导思路（可选参考）

> 本节为探索方向的非约束性建议，不限制执行计划，仅提供思路参考。执行者可选择采纳、部分采纳或完全忽略。

### 2.1 多角色 / 多视角数据生成

在生成教师数据时，可尝试以不同角色或职业背景来生成训练样本，以增加数据的多样性和覆盖面：

| 角色 | 生成侧重 | 潜在价值 |
|------|---------|---------|
| 资深 SPC 工程师 | 精确、结构化的规则判断与处置建议 | 标准答案基准 |
| 新手工程师 | 逐步分析、显式推理过程 | 增强推理链多样性 |
| 质量经理 | 从管理视角描述问题影响与优先级 | 提升表达多样性 |
| 统计分析师 | 强调数学计算过程（σ 边界、CPK 公式） | 强化数值推理能力 |

**实施提示**：
- 在系统提示中明确角色描述，生成对应风格的推理链
- 不同角色生成的答案需经过格式规范化，确保输出格式与评测一致
- 若某角色数据导致格式漂移（CPK 提取率下降），可单独剔除该角色数据

### 2.2 教师讲解原理（知识内化型数据）

除标准的"输入数据 → 判断规则 → 输出结论"格式外，可引入"教师讲解知识"类数据：

**样本形式示例**：

```
问：什么是 Nelson Rule 2？它在实际生产中意味着什么？
答：Rule 2 定义为连续 9 个点位于均值同侧（全高于或全低于均值）……
    在实际生产中，这通常意味着存在系统性漂移……
    σ 的大小影响判断灵敏度：当过程能力充足时……
```

**潜在价值**：
- 帮助模型建立规则背后的统计学概念，而非纯粹模式匹配
- 有助于提升弱规则（如 rule2、rule7）的判断准确率
- 增强模型在边界情形下的鲁棒性

**已知风险（round2 经验）**：
- `spc_textbook.jsonl` 曾在 B1～B2 批次中使用，但由于风格与评测格式不一致，导致 CPK 输出丢失；后续批次已弃用
- 若采用此类数据，**必须与评测格式一致的训练样本混合使用**，防止输出风格漂移
- 建议比例：知识型数据 ≤ 10%，结构化判断数据 ≥ 90%

## 3. 常见陷阱与注意事项

> 以下是已知的高频失误，每一条都曾导致实验结果失真或浪费大量 GPU 时间。**每轮实验开始前必须逐条核查。**

### 3.1 评测设计：必须在 prompt 中约定输出格式

**错误**：评测时 prompt 未约束模型的输出格式，依赖解析器从自由文本中提取结果。

**后果**：模型输出正确但格式不规范，提取失败，指标被严重低估。典型案例：Claude-sonnet-4.6 零样本时 rule 推理基本正确，但 cpk_found_rate 仅 0.020，导致 F1=0.232 远低于其真实能力。

**正确做法**：
- prompt 中明确要求输出 **JSON 格式**（或其他固定结构），例如：
  ```
  请以如下 JSON 格式输出：
  {"violations": ["rule1", "rule3"], "cpk": 1.23}
  ```
- 评测脚本统一用 JSON 解析，而非正则从自由文本提取
- 基线评测和 SFT 评测必须使用**完全相同的 prompt 格式约定**，否则对比无效

### 3.2 cutoff_len 必须覆盖最长推理链

**错误**：使用默认或偏小的 `cutoff_len`（如 4096）。

**后果**：长推理链被截断，模型从未学会需要长上下文的规则（如 rule8），召回直接归零。

**正确做法**：训练前先统计训练集中最长样本的 token 数，`cutoff_len` 设为其 **1.2 倍以上**，本项目最小安全值为 **5120**。

### 3.3 epoch 数不超过 3

**错误**：设置 epoch=5 或更多，期望训练更充分。

**后果**：灾难性过拟合，F1 从 0.43 崩溃至 0.15，CPK 提取率从 1.0 跌至 0.43，模型退化为"背诵训练集"。

**正确做法**：固定 **epoch=3**，这是本任务的训练甜点，已被多次实验反复确认。如需更强效果，优先扩充数据量，而非增加 epoch。

### 3.4 LLaMA-Factory 数据集注册必须用绝对路径

**错误**：`dataset_info.json` 中 `file_name` 使用相对路径。

**后果**：LLaMA-Factory 从其安装目录而非项目目录解析路径，导致数据集注册失败，训练无法启动。

**正确做法**：`dataset_info.json` 中的文件路径**必须是绝对路径**。

### 3.5 vLLM 进程必须显式清理

**错误**：eval 结束后直接退出脚本，未杀死 vLLM 进程。

**后果**：vLLM 进程残留，占用 GPU 显存，下一个训练或 eval 任务 OOM 失败。

**正确做法**：eval 完成后按端口杀进程：`kill $(lsof -ti tcp:<PORT>)`，或在 deploy 脚本中注册 `atexit` 清理钩子。

### 3.6 多任务并发 merge 必须隔离 GPU

**错误**：多个 `merge_adapter.py` 任务同时运行，均默认使用 GPU 0。

**后果**：GPU 0 显存溢出（OOM），merge 任务全部失败。

**正确做法**：为每个 merge 任务指定不同 GPU：`CUDA_VISIBLE_DEVICES=<N> python merge_adapter.py ...`
