# 方法论：从项目文档提炼面试叙事

**适用场景**：给定一份技术项目的实验记录/方法论文档，输出一份面试 Q&A，让候选人能准确、深刻、诚实地展示技术深度。

---

## 核心前提

面试考的不是"你做了什么"，而是三件事：
1. **你能否独立解决非标准问题**（诊断能力）
2. **你是否真正理解了发生的事**（不只是执行，而是理解）
3. **你能否从失败中学习**（元认知深度）

这三件事都不在"成功结果"里——它们藏在失败、反直觉发现、和决策的背后理由中。

---

## 第一步：信号提取（Signal Extraction）

从原始文档中找四类"高价值信号"，忽略其余内容。

### 信号类型与定位方法

| 信号类型 | 定义 | 定位关键词 |
|---------|------|-----------|
| **反预期结果** | 数字或结论与直觉相反 | "意外"、"反而"、"却"、数字对比 |
| **失败诊断链** | 出了问题，通过什么过程定位了根因 | "为0"、"崩溃"、"无效"、"静默失败" |
| **非显然决策** | 有多个选项，选了其中一个，为什么 | "选择X而不是Y"、"而不是"、参数值 |
| **定量元认知** | 用数据证明了一个关于"学习/训练/评测"本身的结论 | 对比表格、百分比变化 |

**操作**：通读文档，在这四类处打标记，忽略"顺利完成的步骤"。

### 本项目提取示例

| 信号 | 类型 | 核心价值 |
|------|------|---------|
| 0.110 vs 0.430 → 实为 0.424 vs 0.420 | 反预期 + 元认知 | 质疑自己的评测方法 |
| rule8 所有实验均为 0.00 → cutoff_len 截断 | 失败诊断链 | 静默失败的诊断范式 |
| 去掉49条样本，F1 +9.7% | 反预期 | 数据质量 > 数据数量 |
| rule7 上采样×3 → rule7 无改善 | 反预期 | 上采样 ≠ 规则学习 |
| GRPO clipped_ratio=1.0 → 奖励全0 | 失败诊断链 | RL 静默失败模式 |
| ws 保留技能文档训练 → ns 推理崩溃 | 非显然决策 | 内化 vs 查文档的根本区别 |
| int4 量化损失 8-9% vs 预期 ≤2% | 反预期 | 精确计算任务对量化敏感 |
| 多角色数据 → F1 下降 | 失败诊断链 | 格式一致性 = 训练数据质量维度 |

## 第二步：受众建模（Audience Modeling）

在写问题之前，先想清楚面试官会站在哪个角度问。

### 面试官视角分类

**技术深度面（senior engineer / tech lead）**
- 问"为什么"：为什么这么配置、为什么选这个方法
- 问"怎么发现的"：症状 → 假设 → 验证的诊断过程
- 想区分：执行者（照着文档做）vs 理解者（知道为什么）

**系统设计面（staff / principal）**
- 问"如果生产部署，挑战是什么"
- 问"如何推广到其他场景"
- 问"你会做哪些不同的决策"

**行为面（manager / HR）**
- 问"最大的错误是什么"
- 问"和预期不符时怎么处理"
- 问"如果重来，会怎么做不同"

**操作**：对每个信号，标注它适合回答哪类问题。一个好的信号通常可以回答多类问题。

---

## 第三步：叙事重构（Narrative Reconstruction）

把"实验结果"重构为"问题-诊断-洞察"的叙事链。

### 重构模板

```
[事件] 我观察到 X（现象/数字）
[反常] 这与预期 Y 不符，因为按理应该 Z
[诊断] 我通过 A → B → C 找到了根因
[根因] 真正的原因是 D
[修复] 做了 E，验证了 F
[元认知] 这告诉我，在类似场景下，应该先检查 G
```

### 示例：cutoff_len 信号的叙事重构

```
[事件] rule8 在 Round 1 全部 5 个实验中召回率均为 0.00
[反常] 其他 7 条规则有变化，唯独 rule8 永远为 0，不像是知识问题
[诊断] 
  → 假设：rule8 的推理链在输出末尾，被截断了
  → 验证：统计训练数据输出长度分布
  → 发现：均值 4151 tokens，但 cutoff_len=4096，94% 样本被截断
[根因] rule8 的分析总出现在输出末尾，而整个输出末尾都被 cutoff 截掉了
[修复] 改 cutoff_len=5120，Round 2 rule8 召回从 0.00 → ≥0.38
[元认知] LLM 训练存在"静默截断"陷阱——没有报错，但尾部内容从未被学习。
         诊断模式：如果某个特定维度（尤其是"最后出现的维度"）持续为0，优先检查截断。
```

**关键**：重构时要还原当时的"不确定性"——面试中展示"我当时不知道，通过什么过程推理出来的"比直接说答案更有说服力。

---

## 第四步：价值筛选（Value Filtering）

不是所有信号都值得写成面试题。用三个过滤条件：

### 过滤条件

**条件A：区分度** — 这个问题能区分"做过这件事"和"真正理解了"的候选人吗？
- 通过：上采样为什么对 rule7 无效（需要理解决策边界 vs 正例数量）
- 不通过：训练用了多少 GPU（事实记忆，无法区分理解深度）

**条件B：可追问性** — 这个答案自然地引出 1-2 个追问，且追问有好答案吗？
- 通过：GRPO 零奖励 → 追问"clipped_ratio 是什么"→"如何修复"→"为什么要看这个指标"
- 不通过：用了哪个框架（LLamaFactory）→ 追问空间很小

**条件C：反直觉性** — 答案与大多数人的直觉相反吗？
- 通过：更多数据反而导致 F1 下降；上采样对目标规则无效
- 不通过：更大的学习率导致更快收敛（符合直觉）

**操作**：对每个候选信号打分（A/B/C 各1分），≥2分的写入面试题，1分以下的丢弃。

---

## 第五步：答案结构化（Answer Structuring）

每个答案遵循三层结构，不要只给结论：

```
【核心答】1-2句话直接回答问题
【证据】支撑核心答的定量数据或具体事件
【教训/泛化】这个经验在其他场景如何应用
```

### 可选增强（视问题类型）

- **诊断类问题**：加"症状→假设→验证"的过程链，展示推理过程
- **决策类问题**：加"排除的替代方案"，展示决策的非唯一性
- **失败类问题**：加"当时为什么没发现"，展示诚实的自我审视
- **元认知类问题**：加"如果重来会怎么做"，展示可迁移的学习

---

## 第六步：质量检验（Quality Check）

写完所有 Q&A 后，用以下标准过一遍：

### 检验清单

- [ ] **有没有"我不知道"**：至少有 2-3 个问题的答案承认了当时的不确定性或错误
- [ ] **有没有失败**：至少 1 道专门讨论"犯了什么错误"的问题
- [ ] **数字够不够**：每个关键结论都有定量支持（F1 数值、百分比、样本数）
- [ ] **追问能回答吗**：对最重要的 3-5 道题，模拟追问"为什么"，答案要能自圆其说
- [ ] **有无过度包装**：如果某个结果其实没有那么好，是否如实说了？

---

## 方法总结：五个核心操作

```
1. 找信号    → 在文档中标记：反预期 / 失败链 / 非显然决策 / 定量元认知
2. 建模受众  → 判断每个信号适合哪类面试问题（技术深度 / 系统设计 / 行为）
3. 重构叙事  → 把"实验结果"还原为"问题→诊断→洞察"的时间序列
4. 过滤价值  → 保留"有区分度 + 可追问 + 反直觉"的信号，丢弃事实记忆类
5. 结构化答案→ 核心答 + 证据 + 教训，诊断类加推理过程，失败类加诚实审视
```

---

## 适用范围与局限

**适用**：
- 有大量实验记录的 ML/工程项目
- 项目持续时间 ≥ 数周、有明显的迭代和失败
- 候选人亲身参与，知道"当时为什么这么做"

**局限**：
- 如果项目全部顺利、无失败，信号稀少，文档质量受限
- 如果只是执行他人方案，缺少"决策背后的理由"这层深度
- 合规/保密约束可能限制数据引用
