# 经验炼金术：将项目经历转化为可迁移知识的方法论

**适用对象**：任何完成过一个项目的人，或帮助别人做事后总结的 AI

---

## 核心认知：所有人都在犯的同一个错误

当项目结束，我们通常会问："我们做了什么？结果怎么样？"

这个问题本身没错，但它抓住的是最不值钱的那层知识。

真正值钱的知识藏在另外两个问题里：
- **"当时为什么这么决定，排除了哪些选项？"**（推理过程）
- **"这说明了什么普遍规律？"**（可迁移原则）

现有所有主流框架（STAR、五问法、AAR、SRE 事后复盘）都只擅长捕捉"做了什么、结果如何"，而系统性地丢掉了推理过程和可迁移原则——恰好是最难重建、最有价值的两层。

---

## 一、现有方法横评

### 主流框架比较

| 框架 | 擅长 | 致命缺陷 | 适用场景 |
|------|------|---------|---------|
| **STAR**（情境-任务-行动-结果） | 最简单的叙事结构，强迫量化结果 | 把复杂推理压缩成单线故事；奖励表达技巧而非理解深度；消除团队贡献 | 初级行为面试，不适合技术深度 |
| **五问法 / Five Whys** | 快速定位单一根因，无需工具 | 假设单一因果链，在软件/ML 系统中失效；不同人分析同一问题得到不同根因 | 制造业简单故障，不适合复杂系统 |
| **AAR（军事事后行动复盘）** | 结构化"计划 vs 实际"差距分析；创造无责氛围 | 教训停在房间里不传播；不质疑原始目标是否正确 | 团队事件复盘，需要中立主持人 |
| **SRE 事后复盘**（Google 版） | 系统性故障根因分析；行动项有 owner 和 deadline | 只适合已发生的事故；不捕捉决策推理质量 | 生产事故，软件系统 |
| **Kolb 经验学习环** | 唯一显式建模"经历→反思→概念化→实验"完整回路 | 步骤顺序与实际学习不符；压力下难执行 | 培训设计，理解学习机制 |
| **双环学习（Argyris）** | 唯一强迫问"我们是否在解决正确的问题" | 无操作步骤，只是诊断视角 | 战略层失误反思 |
| **ADR（架构决策记录）** | 唯一捕捉"考虑过但被拒绝的选项"和决策理由 | 只在决策时填写，不适合事后重建 | 技术架构文档 |

### 我的原始方法（skill_project_to_interview.md）的位置

**做对的**：
- 信号提取（反预期、失败诊断链、非显然决策）——比所有主流框架更好地定位高价值内容
- 价值筛选（区分度 + 可追问性 + 反直觉性）——面试叙事的独特过滤器
- 叙事重构中的"诊断链"——类似 AAR 的结构但更适合技术失败

**缺的**：
- 没有"原则化"步骤：从具体发现提炼可迁移的普遍规律
- 没有 Double-Loop：不问"我们是否在解决正确的问题"
- 没有"被排除选项"：只记录了选择，没记录推理

### 所有框架共同缺失的核心

> **所有框架都捕捉了"发生了什么"，但没有一个系统地捕捉"在不确定条件下，推理过程是什么"。**

这正是最稀缺、最难重建、最有迁移价值的知识。

## 二、综合方法论：四层知识提取

一个完整的项目经历包含四层知识，越往上越值钱，越往下越容易获得：

```
┌─────────────────────────────────────────────────────┐
│  第4层：前提反思   我们是否在解决正确的问题？         │  ← 最稀缺，最常被忽略
├─────────────────────────────────────────────────────┤
│  第3层：原则提炼   这件事说明了什么普遍规律？         │  ← 可迁移的核心
├─────────────────────────────────────────────────────┤
│  第2层：推理重建   当时为什么这么决定？排除了什么？   │  ← 最有深度，最难捕捉
├─────────────────────────────────────────────────────┤
│  第1层：事件记录   发生了什么？计划是什么？差距是什么？│  ← 最容易获得，价值最低
└─────────────────────────────────────────────────────┘
```

大多数人（和 AI）只做了第1层，偶尔做第2层，几乎没有做第3-4层。

---

## 三、操作步骤

### Step 0：准备（读材料前）

**问自己**：这份材料记录的是什么级别的知识？
- 只有结果数字 → 需要主动挖掘第2-4层
- 有失败记录 → 重点在第2层（推理重建）
- 有"意外发现"→ 重点在第3层（原则提炼）

---

### Step 1：事件定位（第1层）

**目标**：找到"高信息密度事件"——不是所有事件，只找以下四类：

| 类型 | 定义 | 识别关键词 |
|------|------|-----------|
| **反预期事件** | 结果与直觉/计划相反 | "意外"、"反而"、数字对比 |
| **失败链** | 出了问题，追溯到了根因 | "为0"、"崩溃"、"无效"、"静默失败" |
| **非显然决策** | 有多选项，选了其中一个 | 配置参数、方案选择、"而不是" |
| **定量反直觉** | 数据证明了一个违反直觉的结论 | 百分比、对比表、"少反而多" |

顺利执行的步骤不是高信息密度事件，跳过。

**工具**：在原始文档上直接标注，每个标注写1行：类型 + 一句话描述。

---

### Step 2：推理重建（第2层）——最关键

这是所有框架都缺失的步骤。

对每个高信息密度事件，还原**当时的不确定性和决策过程**：

```
模板：

[症状]    我/我们观察到了什么异常或现象
[不确定]  当时有哪些可能的解释（不只是事后已知的正确答案）
[诊断过程] 用了什么方法、数据、实验来区分这些解释
[排除了什么] 哪些假设被证伪了，为什么
[决策]    最终做了什么，基于什么标准
[验证]    如何知道这个决策是对的
```

**为什么要填"不确定"和"排除了什么"这两栏**：

这是 ADR 格式的核心洞察——人们记住了选择，忘记了被排除的选项。但被排除的选项恰恰包含了"为什么不这样做"的隐性知识，而这正是别人在类似场景中最需要的判断依据。

**本项目的示例**：

```
[症状]    rule8 在 Round 1 全部实验中召回率为 0.00
[不确定]  可能原因：(a) 训练数据里 rule8 样本太少；(b) 模型能力不足；
          (c) 输出被截断，rule8 分析从未被模型学习到
[诊断过程] 检查数据集中 rule8 样本分布（排除 a）；
          检查其他规则召回——它们有变化（排除 b，能力不是问题）；
          统计训练数据输出 token 长度分布
[排除了什么] 排除了数据不足（rule8 样本占比正常）；
            排除了模型能力（其他规则能学）
[决策]    将 cutoff_len 从 4096 → 5120，覆盖 p100 输出长度
[验证]    Round 2 rule8 召回率从 0.00 → 0.38
```

**填写提示**：如果"不确定"栏写不出来，说明在做事后合理化而非真实还原。真实的诊断过程总是包含错误假设和排除过程。

---

### Step 3：原则提炼（第3层）——从具体到普遍

Kolb 经验学习的核心洞察：**不做这一步，经历就只是经历，不会变成知识。**

对每个推理重建，提炼一条"如果…则…"形式的普遍原则：

```
模板：

[具体发现]  在这个具体场景里发生了X
[边界条件]  这个规律在什么条件下成立？在什么条件下不成立？
[普遍原则]  一般性表述（不依赖具体项目语境）
[可迁移到]  类似这个规律会在哪些其他场景/任务/领域出现
```

**本项目的示例**：

```
[具体发现]  cutoff_len=4096，但训练样本输出均值 4151 tokens，
           导致 94% 样本被截断，rule8（输出末尾）召回=0.00
[边界条件]  适用于所有 LLM fine-tuning；序列末尾的内容比序列
           开头更脆弱；当任务要求"先输出其他内容，最后输出结论"时更严重
[普遍原则]  任何序列模型训练，如果目标输出长度超过 cutoff 限制，
           序列末尾的内容将从未被学习——这是静默失败，没有任何报错。
           截断样本不是"短样本"，是"被强制中止的长样本"，危害比没有该样本更大。
[可迁移到]  GRPO 的 max_completion_length；vLLM 推理时的 max_model_len；
           任何有长度限制的序列生成任务；甚至人类教学中"时间到了就停"的危害
```

**验证原则质量的一个问题**：如果把具体项目名称全部替换掉，这条原则还成立吗？成立 = 真正普遍；不成立 = 还是太具体，需要再抽象。

---

### Step 4：前提反思（第4层）——双环检验

这是 Argyris 双环学习的核心，也是最常被跳过的一步。

**问题**：不只问"我们是否做对了"，还要问"我们是否在做对的事"。

```
检查问题列表（每个项目至少选 1-2 个认真回答）：

□ 我们设定的成功指标，测量的是我们真正想要的吗？
□ 有没有"评测工具本身就是错的"的可能？
□ 如果从零开始设计这个系统，会做哪些不同的根本性选择？
□ 有哪些"当时觉得是约束，其实是可以质疑的假设"？
□ 我们花时间最多的工作，是否贡献了最多的价值？
```

**本项目的示例**：

- 问：0.110 vs 0.430 的比较结果真的测量了我们想要的东西吗？
- 答：没有——提取器是为 SFT 格式设计的，对 Claude 英文输出几乎失效。这个"令人兴奋的结果"实际上是一个测量偏差。
- 洞察：**设定目标指标和设计测量工具是两件事，都可能是错的。当结果"超出预期地好"，应该首先怀疑测量工具，而不是庆祝。**

---

### Step 5：输出适配（面向受众）

以上四步提取的是"原料"。不同受众需要不同的"加工方式"：

| 受众 | 最感兴趣的层 | 输出格式建议 |
|------|------------|------------|
| 技术面试官 | 第2层（推理重建） | 诊断链：症状→假设→验证→根因 |
| 系统设计面试官 | 第2层 + 第4层 | 决策推理 + 前提反思 |
| 行为面试官 | 第1层 + 第3层 | 事件叙事 + 可迁移教训 |
| 技术文档读者 | 第2层 + 第3层 | ADR 格式 + 普遍原则 |
| 团队分享 / 知识沉淀 | 第3层 + 第4层 | 原则列表 + 反思问题 |
| AI 辅助学习 | 全部4层 | 完整模板，不省略任何层 |

## 四、与原有方法的对比

| 维度 | 原方法（skill_project_to_interview） | 本方法 |
|------|--------------------------------------|--------|
| **目标** | 面试叙事准备 | 提取可迁移知识（面试是其中一个输出用途） |
| **核心框架** | 信号筛选 + 叙事重构 | 四层知识 + 五步操作 |
| **推理过程捕捉** | 有"诊断链"，但缺"排除了什么" | 显式要求填写"不确定"和"排除的选项" |
| **原则提炼** | 隐含在"教训"里，不成体系 | Step 3 独立步骤，有明确格式和质量验证 |
| **前提反思** | 没有 | Step 4，使用双环学习检查问题 |
| **受众适配** | 主要面向面试 | 明确区分5类受众，输出格式不同 |
| **学习曲线** | 稍高（需要先理解"信号类型"） | 从四层框架入手，更直观 |

**结论**：两个方法互补——本方法提供更完整的认知框架（适合任何项目反思），原方法的信号筛选和价值过滤（区分度+可追问+反直觉）是本方法 Step 5 面向面试输出时的有效补充。

## 五、一页纸摘要（适合快速参考）

```
项目经历包含四层知识（越往上越值钱，越常被忽略）：

第4层：前提反思   ← 我们是否在解决正确的问题？
第3层：原则提炼   ← 这件事说明了什么普遍规律？
第2层：推理重建   ← 当时为什么这么决定，排除了什么？
第1层：事件记录   ← 发生了什么，结果如何？

大多数人只做第1层，STAR/五问法等主流框架只到第2层。

五步操作：
1. [Step 1] 定位高信息密度事件（反预期/失败链/非显然决策/定量反直觉）
2. [Step 2] 重建推理过程（症状→不确定→诊断→排除→决策→验证）
3. [Step 3] 提炼普遍原则（如果…则…，去掉项目名称仍成立）
4. [Step 4] 双环反思（测量工具对吗？目标对吗？）
5. [Step 5] 根据受众适配输出格式

最高价值的内容不是"发生了什么"，
而是"在不确定条件下的推理过程"——这是所有现有框架都系统性丢掉的。
```

## 六、对 AI 做事后总结的特别说明

AI 辅助总结时有一个特殊的认知风险：**事后合理化偏差**（hindsight bias）。

因为 AI 读到的已经是结果，容易把"当时的不确定性"重建为"显然的正确路径"。

**对策**：
- Step 2 的"不确定"栏和"排除了什么"栏，AI 不能自行填写——必须从原始文档中找到证据（"当时记录了哪些假设？"、"尝试了但失败的方向是什么？"），没有证据就明确说"无法重建"
- Step 4 的前提反思，AI 应该主动问"原始文档是否包含对成功指标本身的质疑？"如果没有，这正是前提假设从未被检验过的证据
- 不要把成功的最终结果反向投影为"从一开始就应该这么做"——推理过程的价值在于它当时是真实的，不是事后合理化的
