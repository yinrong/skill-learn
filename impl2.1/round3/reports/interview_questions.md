# 面试准备：SPC 技能内化项目深度问答

**项目背景**：将 SPC Nelson 8条规则分析能力通过 SFT 内化到 Qwen3-14B，目标是无技能文档推理（ns）达到 F1 ≥ 0.50。历经 Round 1-3，完成 20+ 次训练实验，最终最优 F1=0.420（R3-AB-v2）。

---

## 一、问题定义与架构决策

### Q1：为什么选 SFT 内化，而不是 RAG 或 Prompt Engineering？

**核心答**：三种方案不等价，解决不同问题。

RAG（每次推理带技能文档）有效但存在两个硬伤：
- **推理成本**：500 token 系统提示 × 每次请求 = 规模化后的真实开销
- **知识泄露风险**：系统提示可能被提取攻击获取，不适合包含商业规则的专有知识

Prompt Engineering（直接让基座模型做）：Claude 原始 F1=0.424（我们后来才测出来的公平值），但 CPK 提取率 0.88，输出格式不稳定，无法可靠集成到生产流水线。

SFT 内化的目标不是"让模型知道规则"（Claude 已经知道了），而是**让模型用固定格式、100% 可靠地输出答案**。最终 CPK 提取率从 0.88 → 1.000，这才是工业部署需要的。

**元认知**：最初设定"SFT 超越 Claude 教师模型"为成功标准，后来发现这个假设本身有问题——评测标准对两者不公平。修正评测方法后，真正的成功标准应该是"格式可靠性 + 推理成本降低"，而不是 F1 绝对值超越 Claude。

---

### Q2：ws（with-skill）和 ns（no-skill）格式有什么区别？这个设计背后的直觉是什么？

**核心答**：这是整个方法论最关键的一步。

```
ws 格式（教师数据生成阶段）：
  System: <500 token 技能文档，包含全部 8 条规则>
  User: <任务>
  Assistant: <think>逐步推理</think> <结构化答案>

ns 格式（实际训练格式）：
  System: ""  （空，或通用描述）
  User: <任务>
  Assistant: <think>逐步推理</think> <结构化答案>
```

区别只有 System。但效果天壤之别。

**直觉**：Transformer 学习时会找"最短路径"。如果规则文档在 System 里，模型学会的是"当 System 有规则时，从中查询并应用"——这是一个 **条件行为**，推理时没有文档则崩溃（F1=0.00~0.05）。把 System 清空，模型只能从 Assistant 的 `<think>` 推理链中"抽取"规则，并将其固化到权重。

量化证据：
| 训练格式 | 无技能推理 F1 |
|---------|------------|
| ws（含文档） | 0.00~0.05 |
| 混合 50/50 | 0.20~0.30 |
| ns（无文档） | 0.35~0.43 |

这一步发现在整个项目前期，是通过 Round 1 多次失败实验（expMM/expNN/expPP 均低于 expRR）后归纳出来的。

---

### Q3：你如何设计评测协议来保证公平性？

**核心答**：这是本项目最值得深挖的元认知问题。

最初评测结果：Claude 0.110 vs SFT 0.430，看起来 SFT 大幅超越教师模型，结论令人兴奋。

但有一个疑问：**为什么教师模型（Claude）的学生（SFT）能远超教师？** 这违反了信息论的直觉——学生不可能超过教师从未展示过的能力。

追查发现：regex 提取器是为 SFT 的输出格式（中文结构化报告）设计的，Claude 输出英文分析文本，提取率几乎为零（CPK 提取率 2.5%！）。0.110 不是 Claude 的真实能力，是测量偏差。

**公平化方案**：用 JSON 格式约束 Claude 的输出，替换"写全文报告"指令为"检查后输出 JSON"，从文本末尾提取最后一个完整 JSON 对象。

修正后结果：Claude 0.424 ≈ SFT 0.420——两者基本持平，SFT 的真实优势是格式可靠性（CPK 1.000 vs 0.88）。

**教训**：永远质疑"超出预期的好结果"。当模型明显超越教师时，首先排查测量工具是否有偏。

## 二、数据工程

### Q4：你是如何生成训练数据的？为什么不用真实数据？

**核心答**：合成数据 + 规则引擎验证 = 成本低、质量可控、规则分布可定制。

真实 SPC 数据的问题：
1. 异常样本稀少（生产过程大多正常），规则违反的样本天然不平衡
2. Ground truth 需要领域专家标注，成本高
3. 无法人为构造"边界样本"来攻克弱规则

合成数据流程：
```
确定规则触发概率分布
→ 用 numpy 生成符合分布的时序数据
→ 规则引擎计算 ground truth（确定性）
→ Claude + 技能文档生成推理链
→ 规则引擎验证 Claude 答案（再次过滤）
→ 格式验证（提取器能提取 CPK？）
→ 合格样本加入训练集
```

规则引擎是 oracle——它是确定性的，所以 ground truth 100% 准确。Claude 生成推理链时偶尔出错，用规则引擎过滤后只保留正确答案。

**技术细节**：3 路并行 API 调用是效率与限速之间的平衡点，实测 500 条样本约 2-3 小时生成。

---

### Q5：数据质量 vs 数据数量，你有什么量化证据？

**核心答**：这是本项目最反直觉的发现，有三组数据支持：

**证据一**：textbook 混入
- Round 1 expMM/expNN（混入教科书文本）：F1=0.273~0.279
- expRR（纯净 ns，200条）：F1=0.358
- 减少数据量（混合→纯净），F1 反而提升 +0.079

**证据二**：去截断（最关键）
- R3-AB（1180条，含截断样本）：F1=0.383，CPK率=0.835
- R3-AB-v2（1131条，过滤掉49条截断样本）：F1=0.420，CPK率=1.000
- 删除 49 条（减少 4.1% 数据），F1 提升 +0.037，CPK 率恢复至 1.000

**证据三**：继续增加数据无效
- R3-AB-v2（1131条）：F1=0.420
- R3-AB-v3（1770条，+640条新样本）：F1=0.418（-0.002）
- 增加 57% 数据，F1 几乎不变

**结论**：截断样本不是"短样本"，是"被强制中止的长样本"。模型从中学到的是"在某个点突然停止输出"的行为，这比没有这个样本更差——它是负样本，不是中性的。

---

### Q6：cutoff_len 截断问题是怎么发现的？

**核心答**：症状是 rule8 召回率持续为 0.00，所有 Round 1 实验无一例外。

**诊断过程**：
1. 注意到 rule8 在所有实验中都是 0.00，其他规则有变化
2. rule8 是 Nelson 第 8 条规则——如果是知识问题，应该偶尔触发，不会永远为 0
3. 推测：是不是 rule8 的推理链在输出末尾，被截断了？
4. 统计训练数据输出长度：均值 4151 tokens，p95 约 5000+
5. cutoff_len=4096：94% 的样本被截断，rule8 的分析总在输出末尾，全部被截去
6. 将 cutoff_len 改为 5120 后，Round 2 的 rule8 召回率立刻从 0.00 → ≥0.38

**诊断模式**：当某个特定规则（尤其是"最后一条规则"）召回持续为 0，且排除了数据不平衡原因后，几乎可以确定是截断问题。

**扩展教训**：在设计训练流程时，**必须先统计输出长度分布，再设置 cutoff_len**。这是最容易被忽视、危害最大的配置错误——失败静默发生，没有任何报错。

## 三、模型行为与弱规则突破

### Q7：为什么 rule7 这么难训练？上采样为什么无效？

**核心答**：这涉及模型的归纳偏置与规则的认知难度。

**rule7 内容**：连续 15 个点全部落在均值 ±1σ 以内 → 触发（"过于稳定 = 异常"）

**难点根源**：这是反直觉规则。"稳定"在人类和模型的先验中是"好的"，而这条规则说稳定到极端反而异常。模型在没有额外引导的情况下，会将 15 点全在 ±1σ 内识别为"正常无异常"。

**为什么上采样无效**：R3-AB-v4 将 rule7 样本 3× 上采样（1131→1935条），rule7 召回没有改善（0.389→0.278，反而略降）。

原因：上采样只增加了正例数量，但没有让模型学习到决策边界。模型已经看过足够多的"rule7 触发"样本，知道这条规则存在，但不知道触发和未触发的关键区分点在哪里。

**有效方法**：对比样本对——一个触发样本（15点全在±1σ内）+ 一个未触发样本（第15点略超出±1σ），仅最后一个数据点不同。让模型看到"这一个点的差异决定了是否触发"，才能真正学习决策边界。

**意外发现**：rule7 上采样意外改善了 rule2（0.414→0.552）。推测：rule7 样本的推理链中大量展示了"逐点连续判断"的计数逻辑，间接帮助 rule2（9点同侧）的数数技能提升。这说明规则之间的推理技能存在迁移。

---

### Q8：GRPO 为什么 F1=0.000？你是怎么诊断的？

**核心答**：这是一个 RL 训练的典型静默失败模式。

**表面现象**：R3-C（GRPO）训练完成，无报错，但评测 F1=0.000。

**诊断步骤**：
1. 检查奖励函数：rule_f1 + cpk_bonus + format_bonus，逻辑正确
2. 检查训练日志：发现 `clipped_ratio = 1.0`（100% 截断率）
3. clipped_ratio=1.0 意味着：所有生成样本都超过了 `max_completion_length` 并被截断
4. 截断后的输出不完整 → 奖励函数无法提取答案 → 所有样本奖励=0
5. 奖励全为 0，梯度全为 0，策略从未更新
6. 评测时模型等同于基础模型，基础模型没有学过格式，F1=0.000

**根因**：`max_completion_length=2048`，而 SPC 完整答案均值 4151 tokens，p95 约 5500 tokens。所有生成都被截断。

**修复**：GRPO 的 `max_completion_length` 必须 ≥ 任务答案的 p95 长度。对 SPC 任务，应设置 ≥ 6000。

**元认知**：GRPO/PPO 等 RL 方法的失败比 SFT 更难诊断，因为"训练成功完成"不等于"策略在学习"。关键诊断指标：clipping ratio、entropy、KL divergence——这些比 loss 更能反映策略是否在有效更新。

---

### Q9：量化（QLoRA）对这个任务的损失比预期大，原因是什么？

**核心答**：量化损失取决于任务对精度的敏感性。

**数据**：
- 14B bf16 LoRA（全精度）：F1=0.420
- 14B QLoRA int4：F1=0.394（-6.2%）
- 14B QLoRA int8：F1=0.391（-6.9%）
- 一般预期量化损失 ≤ 2%

**为什么损失超预期**：SPC 任务的核心操作包括：
1. 数值计算：均值、标准差、CPK（浮点数运算）
2. 边界比较：某点是否超过 μ ± 2σ（±0.1% 误差就会误判）
3. 计数：连续 9 点是否同侧（精确计数，不容错误）

int4 量化将权重从 bf16（~65536 个离散值）压缩到只有 16 个离散值。对于文本生成任务，16 个值的精度足够。但对于边界判断的精确计算，微小的权重偏差会累积为判断错误。

**设计原则**：**如果任务包含精确数值计算或边界判断，int4/int8 量化损失可能远超预期，需要提前实测而不是直接假设 ≤2%。**

然而量化也有优势——综合得分（任务F1 × 通用能力保留 / 推理成本）最高的是 14B int8，因为推理显存 ~20GB（是 bf16 的 1/5），大幅降低部署成本。

## 四、系统设计与工程

### Q10：如何在有限资源下完成 20+ 次实验？你的实验管理方法是什么？

**核心答**：实验管理的核心是"最小化变量 + 最大化可重现性 + 快速 fail"。

**具体做法**：

**1. 每轮实验只改一个变量**
- Round 1 → Round 2：专注修 cutoff_len（一次只改这一件事）
- Round 3 各实验：每个实验明确目标（R3-A=弱规则，R3-B=扩数据，R3-D=量化）

**2. 标准化评测流程**
```bash
# 训练完成后立刻跑评测，写入 results/{实验名}.json
# 所有 JSON 同一 schema，方便后续自动对比
```

**3. 快速 smoke test 发现配置错误**
- 训练前先用 3-5 条样本过一遍完整流程
- 检查 cutoff_len 是否截断：统计输出长度分布
- 检查 format：提取器能否在 5 条上正常工作

**4. 不同层次的实验有不同 checkIn 标准**
- Round 1（200 样本，125步）：快速验证方向，3-4小时出结果
- Round 3（1131 样本，5 epoch）：8小时，只有通过 Go/No-Go 才进入 Round 4

**教训**：Round 3 最大的时间浪费来自 R3-B 引入多角色 ws 数据，导致格式漂移、F1 下降。这种错误本可以用 5 条数据的格式验证提前发现，节省 8 小时训练时间。

### Q11：你的综合评分指标如何设计？为什么不只看 F1？

**核心答**：工业部署场景下，F1 只是一个维度。综合得分 = 任务能力 × 通用能力保留 / 推理成本。

```
综合得分 = F1 × (1 - 退化率) / (推理时间_s × 推理卡数 × 单卡显存_GB) × 1000
```

**背后的权衡**：
- `F1`：任务核心指标，不可妥协
- `(1 - 退化率)`：SFT 会导致通用能力下降（本项目 gsm8k 降了 18.7%），这对"全能助手"类产品是严重缺陷
- `推理时间 × 卡数 × 显存`：部署成本，直接影响 ROI

**结果**：纯 F1 最高的是 14B bf16（0.420），但综合得分最高的是 14B int8（0.428），原因是 int8 的显存占用只有 bf16 的 1/5。如果部署场景是低成本推理，int8 是更好的选择。

**追问**：退化率评测用了哪 6 个基准？
答：MMLU、HumanEval、GSM8k、HellaSwag、ARC-C、TruthfulQA（标准通用能力基准集）。GSM8k 数学推理损失最大，原因与量化损失类似——领域 SFT 的训练信号集中在"SPC 推理链"，对 GSM8k 所需的通用数学推理形成了轻微的覆盖/遗忘。

### Q12：多卡训练的配置选择逻辑是什么？

**核心答**：根据"模型是否装得下单卡"和"数据量是否值得并行"两个维度决定。

| 场景 | 方案 | 理由 |
|------|------|------|
| 14B bf16，单卡 H20（80GB）| 单卡直接训 | 能装下，无需分布式开销 |
| 14B，数据量大（1935条） | 3卡 DDP | 加速 3×（8h→3h），effective batch=24 |
| 32B QLoRA | 4卡 FSDP（DeepSpeed ZeRO-3） | 单卡放不下，必须分片 |
| 72B（规划中） | 8卡 ZeRO-3 | 参数量要求多卡 |

**DDP vs FSDP**：DDP（数据并行）每卡保留完整模型副本，适合模型能装下单卡的场景；FSDP/ZeRO-3 将参数分片，适合单卡装不下的大模型。

**Effective Batch Size 的重要性**：3卡 DDP 的 effective batch = 8 × 3 = 24，总训练步数缩短 3×，但每步看到的数据更多，梯度更稳定。

## 五、元认知与架构洞察

### Q13：整个项目中你犯了哪些最重要的错误？

**核心答**（这类问题考查自我批判能力，要诚实而有深度）：

**错误一：没有及早质疑评测指标**（最重要）
- 早期看到 0.110 vs 0.430 时应该立刻警觉，但花了几轮实验才发现是提取器偏差
- 教训：评测方法的有效性和任务本身同等重要，尤其是比较 baseline 时

**错误二：Round 3 引入多角色数据前没有做格式验证**
- R3-B 增加 200 条多角色 ws 数据，F1 从 0.430 下降到 0.372
- 只需要 5 条数据的提取器验证就能提前发现格式不一致
- 教训：任何新的数据来源入训练集前，必须先验证格式兼容性

**错误三：Round 1 cutoff_len 设置没有先统计输出长度**
- 直接用了框架默认值 4096，导致 94% 样本被截断，浪费了整个 Round 1 的算力
- 教训：LLM 训练有几个"静默失败"的关键配置（cutoff_len、max_model_len、max_completion_length），每次开新任务必须先量化这些参数再配置

**错误四：GRPO 配置没有预先估算 max_completion_length**
- R3-C 整次训练完全无效，原因是 max_completion_length=2048 vs 实际需要 6000+
- 教训：RL 训练前必须先统计答案长度分布

### Q14：这个项目最核心的元认知洞察是什么？

**核心答**：

**洞察一：学习的目标决定了学习的方式**

模型"学会 rule7"和"训练时看过很多 rule7 样本"是两回事。rule7 上采样 3× 没有效果证明了这一点。真正的学习发生在模型需要区分"有 rule7 vs 无 rule7"的边界时——这需要对比样本，不需要更多正例。

**洞察二：格式与知识不可分离**

SFT 的价值不是让模型"知道"更多规则（Claude 已知），而是让模型在**正确格式**下**可靠地应用**规则。CPK 提取率 1.000 vs 0.88 这个差距，在生产环境中是"可用"和"需要人工兜底"的差距。

**洞察三：训练数据中的负样本比正样本更难设计但更有价值**

所有人的直觉是"增加想学的规则的样本数量"，但真正有效的是"增加展示判断边界的对比样本"。这在任何需要精确分类的任务中都成立。

**洞察四：评测工具是实验的第一公民**

评测脚本的偏差是"不可见的实验变量"，它会让你花大量时间优化一个假目标。每次引入新的比较对象（Claude、不同格式的数据），都必须首先验证评测工具对两者是否等价。

### Q15：如果从零开始设计这个系统，你会做哪些不同的选择？

**核心答**：

**1. 第一天就建立 JSON 标准化评测**
不使用 regex 提取器，从第一天就要求模型输出 JSON，用 JSON 解析器评测。这样 Claude baseline 和 SFT 可以用同一套工具评测，避免提取器偏差。

**2. 先做 10 条数据的全流程验证（smoke test）**
在生成 200 条训练数据之前，先用 10 条数据跑完整流程：生成→格式验证→训练→评测。确认所有配置（cutoff_len、max_model_len、评测脚本）正常后再扩规模。

**3. 把 rule7 这类反直觉规则单独立项**
在 Round 1 就应该识别出 rule7 的特殊性（"反直觉"规则需要不同的数据策略），而不是到 Round 3 才专门针对。可以在 Round 1 设计时就做 per-rule 难度分析。

**4. GRPO 应该与 SFT 并行而不是串行**
GRPO 需要 SFT 的 checkpoint 作为起点，但 GRPO 的配置（max_completion_length）可以在 Round 1 就确定好。Round 3 才发现 max_completion_length 不够是因为没有提前做参数估算。

## 六、技术深度追问

### Q16：LoRA rank=128、alpha=256 是怎么选的？

**核心答**：rank=128 是这类任务（程序性推理）的经验起点，不是随意选的。

- **lora_rank**：控制适配矩阵的秩（可学习参数量）。rank 越大，模型可以学习越复杂的变换，但 VRAM 占用和过拟合风险增加。SPC 任务需要学习 8 条规则的精确逻辑 + CPK 计算方式，复杂度中等偏高，rank=64 可能不够，rank=256 对 1000 条样本可能过拟合，128 是经验性折中。
- **lora_alpha=256（= rank × 2）**：Alpha 是 LoRA 的缩放因子，控制新权重对原权重的影响比例。alpha/rank = 2 是常用的"不过激"设置，保留原始权重的稳定性同时允许有效学习。
- **lora_target: all**：对所有线性层应用 LoRA，而不只是 Q/V 矩阵。对需要整体推理模式改变的任务（SPC 分析），全层适配比只改注意力矩阵效果更好。

实际上这些参数没有做大规模消融——做了 lr 消融（1e-4 vs 5e-5），rank 没有单独消融，是基于社区经验和初步验证后确定的。这是实验预算有限时的合理取舍。

### Q17：如何在有偏的训练数据下保证模型的泛化性？

**核心答**：本项目用了三个机制。

**1. 生成器多样性**：每批数据使用不同随机种子，保证输入数据分布足够多样（25个采样点的值、USL/LSL 范围、触发规则的组合）。

**2. 规则触发概率的合理设置**：真实 SPC 数据中大多数时候"无违规"。训练数据中如果违规比例过高，模型会偏向预测违规（高召回、低精度）。需要在生成时控制每条规则的触发概率接近真实分布。

**3. 测试集使用完全不同的随机种子**：训练和测试的种子隔离，确保测试集不包含训练时见过的任何数据点。200 条测试集大概有 ±0.01 的 F1 置信区间。

**局限**：本项目的泛化测试限于合成数据。真实 SPC 数据的噪声模式、传感器漂移等特性在合成数据中没有体现。这是合成数据的固有局限。

### Q18：vLLM 部署时遇到了什么坑？

**核心答**：有两个值得记录的问题。

**问题一：TP>1 与并发评测的兼容性**
vLLM 在 TP=4（Tensor Parallelism=4 卡）下，并发多个推理请求时会出现 `EngineDeadError`——推理引擎崩溃。原因是 Qwen3 的 vLLM 实现在 TP>1 时的并发处理有 bug（版本 0.6.x）。

解决：评测时用 TP=1（单卡），concurrency=1（串行），速度慢但稳定。多卡的价值在训练而不是评测时。

**问题二：max_model_len 必须与训练 cutoff_len 一致**
vLLM 的默认 max_model_len 可能低于训练时的 cutoff_len=5120。如果 vLLM 的 max_model_len=4096，模型输出超过 4096 tokens 的部分被截断，rule8 等末尾规则丢失。

解决：部署时显式设置 `--max-model-len 5120`，与训练配置严格一致。

## 七、展望与开放问题

### Q19：F1=0.420，距离目标 0.50 还有差距。你认为突破点在哪里？

**核心答**：基于实验数据，瓶颈不在"样本数量"，而在三个具体方向：

**1. 弱规则对比样本（P0，最高优先级）**
rule7（0.389）和 rule2（0.276）仍然是最大的拉低因子。通过正负对比样本对，这两个规则理论上可以达到 0.6+ 的召回率。如果 rule7 从 0.389→0.6、rule2 从 0.276→0.6，整体 F1 估算能提升约 +0.05~0.08。

**2. GRPO 强化训练（P1）**
SFT 的上限是教师数据质量。GRPO 直接优化 rule_f1，可以突破教师的上界。关键配置：max_completion_length ≥ 6000，trl ≥ 1.3.0（LlamaFactory 的 GRPO 不支持 Qwen3 template）。

**3. 更大的基础模型（P1）**
32B int4 在量化损失下 F1=0.379，远低于 14B bf16=0.420。但 32B bf16 全精度训练（需要 ~200GB）理论上 F1 上界更高。量化是部署需求，但训练阶段应该用 bf16。

### Q20：这套"技能内化"方法论可以推广到哪些场景？有哪些局限？

**核心答**：

**适用场景**：
- 规则明确且数量有限（≤50条，可以写成技能文档）
- 有确定性 oracle 验证答案（如规则引擎、数学验证器、编译器）
- 推理延迟敏感（不能每次请求带 500+ token 系统提示）
- 知识需要保密（规则不能暴露在上下文窗口中）

**局限**：
- **规则不稳定**：如果规则频繁更新，每次都要重新 SFT，成本高。RAG 在这种场景更灵活。
- **规则数量过多**：超过 100 条规则时，训练数据需求增长很快，合成数据也难以覆盖所有组合
- **通用能力退化**：SFT 会降低通用能力（本项目 gsm8k -18.7%），不适合"既要专业又要全能"的部署场景
- **合成数据分布漂移**：本方法依赖合成数据，如果真实数据分布与合成数据有显著差距，泛化性未知
