## 一、背景与动机

### 1.1 四大落地场景

```
                          ┌──────────────┐
                          │   决策大脑    │  全局优化 / 图推理 / 跨 Agent 仲裁
                          │ (Decision Brain) │
                          └──┬────────┬──┘
               汇聚输出 + 全量数据  │        │  汇聚输出 + 全量数据
                    ┌──────┘        └──────┐
                    ▼                      ▼
             ┌────────────┐         ┌────────────┐
             │ 装备 Agent  │         │ 线长 Agent  │
             │ 参数/物料/SPC │        │ 排班/OEE/协调│
             └────────────┘         └────────────┘
                    │                      │
                    └──────┐  ┌────────────┘
                           ▼  ▼
                    ┌──────────────┐
                    │ 工厂问答系统  │  知识检索 / SOP / 故障诊断
                    └──────────────┘
```

| 场景 | 核心功能 | 典型用户 | 对模型的核心要求 | 标杆借鉴 |
|------|---------|---------|--------------|---------|
| **装备 Agent** | 参数调试（示教/优化/自动补偿）、物料管理（抛料/调 spec/收严）、动态调优、异常检测（SPC/CPK） | 装备工程师、工艺工程师 | 精确数值推理、工业协议理解、低延迟工具调用、时序异常识别 | 借鉴 **Siemens Industrial Copilot** TIA Portal 深度集成思路（OPC-UA/Modbus/PLC 原生理解）；借鉴 **Qwen3** MCP 原生工具调用保证格式稳定；借鉴 **Claude Sonnet 4.6** 混合推理（日常快速响应，复杂故障切换深度思考）；借鉴 **Claude Opus 4.5** 持续长任务运行能力（巡检/监控场景） |
| **线长 Agent** | 产线自动化管理：排班、换型、OEE 监控、跨工序协调 | 线长、生产主管 | 多步骤规划、跨系统工具调用（MES/ERP/SCADA）、中文口语理解 | 借鉴 **Rockwell FactoryTalk** PLC/SCADA 集成模式（跨系统协调）；借鉴 **Qwen3** 128K 上下文（班次日志/工艺规程完整理解）；借鉴 **Claude Sonnet 4.6** MCP 工具调用（MES/ERP/SCADA 多系统稳定联动） |
| **决策大脑** | 全局决策中枢：汇聚装备/线长 Agent 输出及全量产线数据（传感器、MES、ERP、质量、物料），执行图推理（知识图谱/因果图/工序关联图）与常规推理程序，输出全局优化决策（排产、质量策略、维护计划） | 工厂厂长、生产总监、工艺总工 | 多源异构数据融合、图推理（GNN/知识图谱推理）、与常规优化/推理引擎混合调用、跨 Agent 编排与仲裁、全局约束满足 | 借鉴 **Claude Sonnet 4.6** 多 Agent 编排能力（agentic SOTA，编排与仲裁）；借鉴 **Claude Opus 4.5** 持续数小时运行（全局优化计算周期长）；借鉴 **Qwen3** /think·/no_think 混合推理（决策大脑默认深度思考模式）；图推理与常规推理程序混合调用为工业场景原生需求，需自研 |
| **工厂问答系统** | 知识检索、SOP 查询、故障诊断、培训辅助 | 工人、管理人员、工程师、数据/算法工程师 | 广泛工业知识覆盖、角色自适应输出风格、准确引用标准文档 | 借鉴 **Claude Sonnet 4.6** 1M 上下文（设备手册/标准文档完整理解）；借鉴 **Gemini 3.1 Pro** 原生多模态（图纸/仪表读数/SPC 控制图截图识别）；借鉴 **Qwen3** 混合推理（简单查询低延迟，复杂诊断深度思考） |

四大场景之间的协作关系：装备 Agent 与线长 Agent 分别负责设备级和产线级的实时执行；**决策大脑**位于顶层，汇聚两者的输出及工厂全量数据，通过图推理和常规推理程序的混合调用做出全局优化决策；工厂问答系统面向所有角色提供知识服务，并作为各 Agent 决策依据的知识底座。

**微调策略与资源规划**：工业场景下 LoRA/QLoRA 可达到全量微调 90–95% 的效果，推荐以参数高效微调（PEFT）为主。4×H100 即可起步训练 32B 模型，覆盖四大场景核心需求。

> - 微调方法详细对比（LoRA / QLoRA / DoRA / LoRA+ / Full FT）→ 见 [第六章 §6.7 参数高效微调](#67-参数高效微调peft策略)
> - 各场景 GPU 资源方案与档位对比 → 见 [第七章 §7.2 资源需求](#72-资源需求)

### 1.2 通用模型的工业缺口

通用 LLM 在工业场景存在三层系统性缺口（详见 `doc/industrial-foundation-model.md`）：

#### A. 能力层缺口（模型本身能力不足）

| 缺口 | 具体表现 | 影响场景 |
|------|---------|---------|
| **领域语言贫乏** | 对 ISA-88、IATF-16949、SPC、FMEA、OEE、AQL 等术语理解浅薄 | 全部四大场景 |
| **约束推理缺失** | 无法验证 RPN = S×O×D，无法判断控制图 UCL > CL > LCL 合规性 | 装备 Agent、决策大脑 |
| **数值精度缺失** | 工艺参数差 0.1°C 可能导致废品，通用模型对数值敏感度不足 | 装备 Agent、决策大脑 |
| **时序因果弱** | 无法识别跨工序质量传递链路，无法建立时序因果关系 | 决策大脑、线长 Agent |
| **模态盲区** | 不能原生理解时序传感器流、PLC 梯形图、P&ID 图、工业视觉图像 | 装备 Agent、决策大脑 |
| **隐性知识缺失** | 工厂口语、班组协作、异常升级链路、责任边界等隐性流程知识难以覆盖 | 线长 Agent、工厂问答 |

#### B. 工程层缺口（部署与集成障碍）

| 缺口 | 具体表现 | 影响场景 |
|------|---------|---------|
| **上下文无记忆** | 每次会话从零开始，无法持续跟踪设备状态与产线上下文 | 装备 Agent、线长 Agent |
| **记忆膨胀与成本失控** | 长上下文带来 token 成本和延迟，压缩总结导致关键信息丢失 | 决策大脑（数据量最大） |
| **工具集成可靠性上限** | 工具调用格式漂移、长任务漂移、prompt injection 风险 | 装备 Agent、线长 Agent、决策大脑 |
| **版本漂移与不可重复** | 闭源模型迭代不可控，同一任务不同时间输出差异，无法通过 IATF/ISO 验证流程 | 全部四大场景 |

#### C. 治理层缺口（安全与合规）

| 缺口 | 具体表现 | 影响场景 |
|------|---------|---------|
| **幻觉与可验证性不足** | 数值/单位/边界条件/工艺约束易出错，工业场景要求”可验算/可回放/可追责” | 装备 Agent、决策大脑 |
| **可审计与合规不足** | 闭源 API 在数据出域、留存策略、审计取证方面存在天然限制 | 全部四大场景 |
| **安全边界缺失** | 存在人身/设备安全风险，高危操作需二次确认/工单审批/权限校验 | 装备 Agent、决策大脑 |

> 注：本白皮书后续版本将对所有事实类/总结类信息补齐可核验引用，并将来源集中沉淀在 `doc/post-train/sources/` 目录中。

### 1.3 后训练核心目标

**落地策略判断**：
- 若主要瓶颈是”知识缺口”，可优先用 RAG / 工具补齐。
- 若主要瓶颈是”准确性、可审计、成本、版本可控、工具可靠性上限”，则需要**私有化部署 + 后训练 +（必要时）替换为可控的开源/自研基座**。
- 决策大脑的图推理与混合推理需求，进一步要求模型具备**外部推理引擎调用能力**，而非纯粹依赖 LLM 内部推理。

**后训练的核心目标**：将上述三层缺口（能力 / 工程 / 治理）及标杆能力内化为模型默认行为，而非依赖运行时提示工程。具体而言：

1. **补齐能力层**：工业领域知识、约束推理、数值精度、时序因果、多模态理解
2. **借鉴标杆能力**：混合推理模式、超长上下文、工具调用原生支持、持续长任务运行、多 Agent 编排
3. **夯实工程层**：结构化状态管理、工具调用可靠性、版本可控与可重复
4. **守住治理层**：幻觉抑制与可验证输出、数据本地化与合规审计、安全边界与拒答策略
5. **决策大脑专项**：图推理能力、与常规优化/推理程序混合调用、跨 Agent 编排与冲突仲裁

## 二、后训练 ROI 分析

### 2.1 投入项

| 投入类别 | 估算规模 | 说明 |
|---------|---------|------|
| **数据标注** | 50K–200K 条 SFT 样本 | 工业 SOP、故障案例、参数调优对话、视觉标注 |
| **算力（训练）** | 100–500 GPU·天 | 7B 模型全量 SFT + RL，A100/H100 |
| **算力（推理）** | 持续运营成本 | 私有化部署节省 API 费用 |
| **工程人力** | 5–10 人·月 | 数据工程、训练框架、评测、部署 |
| **领域专家** | 2–5 人·月 | 工艺/装备工程师标注审核 |

### 2.2 收益项

| 收益维度 | 量化指标（目标） | 说明 |
|---------|--------------|------|
| **替代 API 成本** | ≥60% API 费用节省 | 私有化部署替代 GPT-5/Claude 调用 |
| **响应速度** | 延迟 <500ms（P95） | 工厂现场实时交互需求 |
| **工业任务准确率** | 比通用模型提升 20–40% | 参数推荐、故障诊断、SPC 判断 |
| **数据安全** | 100% 本地化 | 工厂生产数据不出域 |
| **定制化能力** | 可注入专有知识 | 设备台账、内部 SOP、企业标准 |
| **Agent 可靠性** | 工具调用成功率 >90% | 装备 Agent 多步骤任务完成率 |

### 2.3 ROI 估算框架

```
年净收益 = API 替代节省 + 效率提升价值 - 运营成本
         ≈ (月 API 调用量 × 单价差) × 12 + (人效提升 × 人力成本) - 推理服务器成本

典型场景（中等规模工厂）：
  月 API 调用：500M tokens → 节省 ≈ $15,000/月
  私有推理成本：≈ $3,000/月（2×A100 服务器折旧）
  年净节省：≈ $144,000
  
初始投入：≈ $200,000–$400,000（含数据、训练、工程）
回收周期：12–24 个月
```

### 2.4 ROI 敏感性

| 因素 | 高 ROI 条件 | 低 ROI 条件 |
|------|-----------|-----------|
| API 调用量 | >1B tokens/月 | <100M tokens/月 |
| 工业任务准确率提升 | >30% | <10% |
| 数据质量 | 专家标注+审核 | 纯自动生成 |
| 部署规模 | 多工厂复用 | 单一场景 |

## 三、竞品分析

### 3.1 闭源通用模型（主要竞品）

| 模型 | 发布时间 | 核心能力 | 工业场景关键指标 | 局限性 |
|------|---------|---------|--------------|--------|
| **GPT-5.4** | 2026 | 通用推理+代码生成（含低延迟与代码专用变体） | 作为对标基线：通用推理、代码与工具调用能力 | 闭源、API 成本高、数据不出域风险、无工业专用优化 |
| **Claude Sonnet 4.6** | 2026-02 | Agent/长任务/代码，1M 上下文，混合推理（快速+深度思考可控） | 企业文档 Q&A 领先，agentic 任务 SOTA | 闭源、$3/$15 per M tokens，无法私有化 |
| **Claude Opus 4.5** | 2025-09 | 最强 coding，SWE-bench 72.5%，可持续运行数小时 | 复杂多步骤 Agent 最优 | 价格最高（$15/$75），延迟高 |
| **Gemini 3.1 Pro** | 2026 | 原生多模态（文本/图/视频/音频），1M 上下文，ARC-AGI-2 77.1% | GPQA 94.3%，τ²-bench Retail 90.8%，多模态工业视觉潜力最强 | 闭源，Google 生态依赖 |

**结论**：闭源模型能力强但存在数据安全、成本、定制化三大障碍，不适合作为工厂核心推理引擎，可作为**评测基线**和**数据蒸馏教师模型**。

## 四、评测集设计

### 4.1 评测体系总览

工业大模型评测分三层：**通用能力基线**（复用公开评测集）、**工业专项能力**（自建评测集）、**端到端 Agent 任务**（场景仿真评测）。

```
┌─────────────────────────────────────────────────────────┐
│  Layer 3: 端到端 Agent 仿真（最终价值验证）                │
│  装备 Agent 任务完成率 / 线长 Agent KPI / 问答满意度       │
├─────────────────────────────────────────────────────────┤
│  Layer 2: 工业专项能力（核心差异化评测）                   │
│  SPC判断 / 工艺参数推理 / 故障诊断 / 视觉质检 / 工业代码   │
├─────────────────────────────────────────────────────────┤
│  Layer 1: 通用能力基线（公开评测集）                       │
│  GPQA / MMLU / LiveCodeBench / τ-bench / SWE-bench      │
└─────────────────────────────────────────────────────────┘
```

### 4.2 Layer 1：通用能力基线（公开评测集）

| 评测集 | 评测维度 | 工业场景相关性 | 使用目的 |
|-------|---------|-------------|---------|
| **GPQA Diamond** | 研究生级科学推理（物理/化学/生物） | 工艺原理推理类比 | 基础科学推理能力基线 |

## 六、后训练方法选择

### 6.0 前置概念：语言模型的输出本质是概率

理解后训练所有方法之前，需要先理解一件事：**语言模型的输出不是文字，而是概率分布**。你看到的文字只是从概率中"抽奖"的结果。

```
你看到的（和模型对话时）：

  输入: "回流焊峰值温度应为"  →  模型输出: "235°C"

模型内部实际发生的（每生成一个字都重复一次）：

  输入: "回流焊峰值温度应为"
                  ↓
  ┌───────────────────────────────────┐
  │  模型对词表中每个词计算一个概率：     │
  │                                     │
  │  "235"   → 0.42  ← 概率最高         │
  │  "240"   → 0.28                     │
  │  "200"   → 0.08                     │
  │  "the"   → 0.0001                   │
  │  "猫"    → 0.000003                 │
  │  ...（词表约 15 万个词，每个都有概率） │
  └───────────────────────────────────┘
                  ↓
  从概率表中抽奖选一个词（概率越高越容易中）→ 选中 "235"
                  ↓
  把 "回流焊峰值温度应为 235" 作为新输入，再来一次 → 选中 "°C"
                  ↓
  一个字一个字重复，直到生成完整回答
```

**推理（对话）和训练的区别**：

| | 推理（你和模型对话） | 训练（CPT/SFT/DPO/RL） |
|--|-------------------|----------------------|
| 模型做什么 | 算出概率表 → **抽奖选词** → 输出文字 | 算出概率表 → **直接用概率值算 Loss** → 更新参数 |
| 你看到什么 | 生成的文字 | 看不到（后台自动完成） |
| 概率表的用途 | 用来采样出一个词 | 用来衡量"模型认为这段文字有多合理" |

**为什么这很重要**：后续每个训练方法都在"对概率做文章"——
- **CPT / SFT**：让模型对正确文字的预测概率变高（降低 Loss）
- **DPO**：让模型对好回答的概率 > 对差回答的概率（不需要生成文字）
- **RL**：模型真的生成文字（抽奖），然后根据奖励信号调整概率分布

### 6.1 后训练总体路线

| 阶段 | 英文缩写 | 全称 | 通俗解释 | 类比 | 输入 → 输出 |
|------|---------|------|---------|------|-----------|
| **阶段一** | **CPT** | Continued Pre-Training（领域持续预训练） | 让模型大量"阅读"工业文档，把工业术语和知识内化到模型权重中 | 像新员工入职前先读完所有设备手册和行业标准 | 海量工业文本 → 模型"懂工业语言" |
| **阶段二** | **SFT** | Supervised Fine-Tuning（监督微调） | 用人工标注的"问题-标准答案"对来教模型按正确格式回答工业问题 | 像师傅手把手带徒弟，给他看标准的问答范例 | 标注好的对话数据 → 模型"会回答工业问题" |
| **阶段三** | **DPO** | Direct Preference Optimization（直接偏好优化） | 给模型看"好回答"和"差回答"的对比，让它学会分辨哪种回答更专业 | 像考试改卷，告诉模型满分答案长什么样、扣分答案错在哪 | 偏好对（好/差回答） → 模型"知道什么是好回答" |
| **阶段四** | **RL / GRPO** | Reinforcement Learning / Group Relative Policy Optimization（强化学习推理增强） | 让模型反复做可验证的推理题（如计算 CPK），做对有奖励、做错扣分，逐渐提升推理准确率 | 像刷题，但每道题都有标准答案自动判分 | 可验证推理题 → 模型"推理又准又稳" |
| **阶段五** | **VLM** | Vision-Language Model Alignment（多模态对齐） | 让模型学会"看图说话"——理解工业图片（缺陷照片、控制图、仪表读数）并给出分析 | 像培训质检员看缺陷图片、读仪表盘 | 图像+文本标注对 → 模型"能看懂工业图像" |

```
训练流水线：

  CPT（读书学知识）→ SFT（跟师傅学回答）→ DPO（对比好坏答案）→ RL（刷题提推理）→ VLM（学看图）
  
  每个阶段在上一阶段的基础上叠加，逐步从"懂知识"进化到"会做事"。
```

#### 各阶段人工标注需求

| 阶段 | 是否需要人工标注 | 标注内容 | 谁来标注 | 数据量 | 每条耗时 | 总工作量估算 | 降低人工的方法 |
|------|--------------|---------|---------|-------|---------|------------|-------------|
| **CPT** | **基本不需要** | 不需要标注。只需收集、清洗、去重已有的工业文档 | 数据工程师 | 10–50B tokens（原始文档） | — | **1–2 人月**（数据工程，非标注） | 自动化清洗管线：PDF 提取 → 去重 → 质量过滤 → 格式统一 |

### 6.2 阶段一：领域持续预训练（CPT）

**目标**：将工业领域语言内化为模型权重，无需每次提示

**训练原理**：

CPT 的训练方式和大模型预训练完全相同——**预测下一个词（Next-Token Prediction）**。

```
输入文本: "SMT 回流焊的峰值温度应控制在 235–245"
模型任务: 读到 "235–245" 后，预测下一个词 → "°C"

                     ┌─────────────────────────┐
  "SMT 回流焊的峰值温度应控制在 235–245" ──→ │  模型预测: "°C"         │
                     │  正确答案: "°C"         │
                     │  Loss = 预测与正确答案的差距 │
                     └─────────────────────────┘
  Loss 越小 → 模型越懂这个领域的语言模式
```

工作机制：模型逐词阅读工业文档，每读一个词就尝试预测下一个词。预测错了就调整参数，让下次预测更准。读完几十亿词之后，模型就自然"记住"了工业术语之间的搭配关系（比如"CPK"后面常跟"≥1.33"，"Nelson 规则"后面常跟"控制图"）。

**为什么有效**：通用模型在预训练时几乎没见过工业文档，所以遇到 "ISA-88" "FMEA" 等术语时预测能力很差。CPT 就是补上这块缺失的"阅读量"。

**与预训练的区别**：预训练从零开始（随机参数），CPT 在已训练好的模型上继续训练。为避免"读了工业文档就忘了通用知识"（灾难性遗忘），需要混入 30% 通用语料。

**数据构成**（建议总量 10–50B tokens）：

| 数据类别 | 占比 | 来源 | 说明 |
|---------|-----|------|------|
| 工业标准规范 | 15% | ISA-88/95、IATF-16949、ISO 14644、GB/T 系列 | 权威知识内化 |
| 设备技术文档 | 20% | 设备手册、DCS/PLC 说明书、传感器数据表 | 设备知识 |
| 工艺知识 | 20% | SOP、作业指导书、工艺路线、FMEA 文档 | 工艺推理基础 |
| 故障案例库 | 15% | 维修工单、故障报告、根因分析报告 | 故障诊断能力 |
| 工业代码 | 15% | PLC 梯形图、ST 语言、MES SQL、Python SPC 脚本 | 代码生成能力 |
| 工业学术论文 | 10% | 制造工程、质量工程、工业自动化领域论文 | 原理理解 |
| 合成数据 | 5% | 基于 DeepSeek-R1/Qwen3-235B 生成的工业推理链 | 推理能力增强 |

### 6.3 阶段二：监督微调（SFT）

**目标**：对齐工业任务的输入输出格式、角色行为、安全边界

**训练原理**：

SFT 的本质仍然是"预测下一个词"，但有两个关键区别：

1. **数据变了**：不再是纯文本，而是结构化的对话（system → user → assistant）
2. **Loss 只算 assistant 部分**：模型读 system 和 user 的内容但不计算损失，只在预测 assistant 的回答时计算损失

```
对话数据:
  system: "你是装备 Agent..."          ← 模型读取，不计算 loss
  user:   "3号回流焊温度异常"           ← 模型读取，不计算 loss
  assistant: "我先读取温度数据..."       ← 模型预测每个词，计算 loss ✓

                ┌──────────────────────────────────┐
  模型读完 user 的提问后，逐词生成 assistant 的回答：
  
  "我" → "先" → "读取" → "温度" → "数据" → ...
   ↕       ↕       ↕        ↕        ↕
  标准答案对应的每个词
  
  每个位置：模型预测的词 vs 标准答案的词 → 计算交叉熵 Loss
                └──────────────────────────────────┘
```

**不需要人工打分**。"分数"就是模型预测值与标准答案之间的交叉熵损失（Cross-Entropy Loss）——模型生成的回答越接近标准答案，Loss 越低，参数更新越小；偏差越大，Loss 越高，参数调整越大。训练框架自动完成这一切。

**与 CPT 的区别**：
- CPT 是"读课本"——模型学会工业语言的统计规律，但不知道怎么回答问题
- SFT 是"做练习题对答案"——给模型看大量"提问→标准回答"的范例，模型学会在收到类似提问时生成类似格式和质量的回答

**SFT 数据构成**（建议 50K–200K 条）：

| 数据类别 | 数量 | 构建方法 |
|---------|-----|---------|
| 工业问答对（多角色） | 30K | 专家标注 + 模型辅助生成 |
| 装备 Agent 轨迹 | 20K | 仿真环境收集 + 人工审核 |
| SPC/CPK 分析示例 | 10K | 规则生成 + 专家校验 |
| 工艺参数推荐 | 15K | 历史生产数据 + 专家标注 |
| 故障诊断案例 | 20K | 维修工单结构化 + 专家补全 |
| 工业代码生成 | 15K | 自动生成 + 单元测试验证 |
| 多模态工业样本 | 10K | 工业图像 + 文本描述对 |
| 安全拒绝样本 | 5K | 手工构造（涉密/危险操作拒绝） |

### 6.4 阶段三：偏好优化（DPO / RLHF）

**目标**：提升输出的准确性、安全性和工业专业性

**为什么 SFT 之后还需要 DPO**：

SFT 只给模型看"标准答案"，模型学会了"好的回答长什么样"，但不知道"差的回答差在哪"。这导致一个问题：模型在遇到不确定情况时，可能生成"看起来像标准答案但实际有错"的回答（幻觉），因为它从未被明确告知什么是错的。

DPO 通过直接对比好/差回答来补上这一课。

**关键澄清：好回答和差回答不是模型自己生成的**。

DPO 的偏好对是训练**之前**离线准备好的数据。被训练的模型在训练过程中不生成任何回答，它只是"读"这两个现成的回答，分别计算概率，然后调整参数。

```
DPO 数据准备（训练前，离线完成）：

  同一个问题: "SPC 控制图上连续 7 个点在中心线同一侧"

  ✅ chosen（好回答）从哪来：              ❌ rejected（差回答）从哪来：
  · 领域专家亲自写的                      · 未经微调的基础模型直接回答
  · 强模型生成 → 专家审核通过              · 故意构造的数值/标准引用错误
  · SFT 阶段已验证的高质量样本             · 角色不适配（对工人讲公式）

DPO 训练过程：

  模型读 chosen: "触发 Nelson 规则 2..."  → 算概率 P(chosen)
  模型读 rejected: "数据有一定趋势..."     → 算概率 P(rejected)
  调整参数使 P(chosen) > P(rejected)

  ⚠️ 模型全程不生成任何文字，只是评估两段现成文字的概率
```

**对比 RL/GRPO**：RL 阶段模型确实需要自己生成多个回答（通过采样时的随机性——每次随机选不同的词，同一个问题就会产生不同回答），然后由程序自动判分。这是 DPO 和 RL 的根本区别：

| | DPO | RL/GRPO |
|--|-----|---------|
| 回答谁生成 | 训练前离线准备好（人写/其他模型生成） | 训练中模型自己生成 |
| 好坏谁判断 | 数据中已标好 | 程序自动判分（奖励函数） |
| 模型在训练时做什么 | 读两段回答，算概率，调参数 | 生成回答 → 被打分 → 调参数 |
| 需要人工 | 需要（准备偏好对） | 几乎不需要（自动化） |

**训练原理**：

DPO 的损失函数和 SFT 的逐字匹配（Cross-Entropy）**完全不同**：

- **SFT**：要求模型逐字复现标准答案 → "均值偏移"和"过程漂移"虽然同义，但逐字不匹配就会被惩罚
- **DPO**：只要求模型给 chosen 整段话打的概率分 > 给 rejected 整段话打的概率分 → 不要求复现 chosen 原文，只要求排序对

```
DPO 计算过程：

  ① 对同一个 prompt，分别计算模型生成 chosen / rejected 的总概率：
     log P_θ(chosen)  = Σ log P(每个词 | 前文)  = -12.3（概率较高 = 更"顺"）
     log P_θ(rejected) = Σ log P(每个词 | 前文)  = -15.7（概率较低 = 更"不顺"）

  ② 同样计算参考模型（SFT 阶段的模型）的概率（作为锚点，防止过度调整）：
     log P_ref(chosen)  = -13.0
     log P_ref(rejected) = -14.5

  ③ Loss = -log σ( β × [ (log P_θ(chosen) - log P_ref(chosen))
                          - (log P_θ(rejected) - log P_ref(rejected)) ] )

  直觉理解：
    - 模型已经更倾向 chosen → Loss 低，几乎不更新
    - 模型还倾向 rejected → Loss 高，大幅调整参数
    - P_ref 的作用：不是让模型无限偏向 chosen，而是"比 SFT 模型更偏一点就够了"
    - β 控制调整力度（通常 β=0.1，太大容易过度优化）
```

**关于"句式不同但含义相同"的疑问**：DPO 不要求模型复现 chosen 的原文。训练完成后，模型可以用自己的措辞生成回答——只要回答的"方向"对了（像 chosen 而非 rejected）就行。这一点和 SFT 有本质区别。

**DPO 的真正局限与应对**：

| 局限 | 原因 | 应对方法 |
|------|------|---------|
| **长度偏差** | 短回答的 log P 天然比长回答高（词少 → 概率乘积更大），可能导致模型偏好简短回答 | 按回答长度做归一化（SimPO）；或在构建数据时控制 chosen/rejected 长度接近 |
| **偏好对质量决定上限** | DPO 只能区分"chosen 和 rejected 之间的差异"，如果两者差距很模糊，学到的信号就弱 | 构建数据时确保 chosen/rejected 有明确的质量差距（如：数值对/错、有/无标准引用） |
| **只学到"偏好"而非"能力"** | DPO 不教模型新知识，只教它在已有能力范围内做更好的选择 | DPO 放在 SFT 之后——SFT 先灌入能力，DPO 再优化选择 |

**不需要单独训练奖励模型**：这是 DPO 相比传统 RLHF 的最大优势。传统 RLHF 需要先训练一个"评委模型"来打分，再用打分信号训练语言模型（两步，不稳定）。DPO 把这两步合成一步，直接从偏好对中学习（一步，更稳定）。

**偏好数据构建**：
```

  - 领域专家认可的回答
  - 高分 SFT 样本

rejected 来源：
  - 通用模型直接输出（无工业知识）
  - 数值错误的回答
  - 角色不适配的回答（技术术语对工人）
```

### 6.5 阶段四：强化学习推理增强（RL-CoT）

**目标**：增强工业推理能力，参考 MiMo 和 DeepSeek-R1 的 RL 路线

**为什么 DPO 之后还需要 RL**：

DPO 教模型分辨好坏回答，但偏好数据是人工标注的，数量有限。对于需要精确计算的工业推理题（CPK 算到小数点后两位、Nelson 规则逐条判断），靠人工标注不够——答案可以程序化验证。RL 就是让模型"自己刷题"：

```
训练循环（每一轮）：

  ①  给模型一道推理题:
      "焊点偏移量 [12,15,11,...,26]，USL=30, LSL=0，求 CPK"
  
  ②  模型生成 N 个不同回答（N=8，采样多条）:
      回答A: CPK=0.91 ✅    回答B: CPK=1.23 ❌    回答C: CPK=0.91 ✅   ...
  
  ③  程序自动判分（不需要人）:
      回答A: reward=+1.3    回答B: reward=0.0     回答C: reward=+1.3   ...
  
  ④  参数更新:
      增大生成"回答A/C"类回答的概率
      减小生成"回答B"类回答的概率
  
  重复数万轮 → 模型推理准确率从 ~70% 提升到 ~90%
```

**GRPO 的核心机制——"组内相对排名"**：

传统 RL（如 PPO）需要训练一个独立的"评委模型"（Critic）来判断回答好不好。GRPO 省掉了这个评委，改用更简单的方法：

```
GRPO 的做法：
  
  对同一个问题，生成一组回答（比如 8 条），计算每条的奖励分数：
  
  回答 1: reward = 1.3
  回答 2: reward = 0.0
  回答 3: reward = 1.3
  回答 4: reward = 0.5
  回答 5: reward = 0.0
  回答 6: reward = 1.3
  回答 7: reward = 0.5
  回答 8: reward = 0.0
  
  组内平均分 = 0.61
  
  高于平均的回答 → 正向更新（鼓励）
  低于平均的回答 → 负向更新（抑制）
  
  "好不好"不是绝对标准，而是在这组回答中相对排名。
  这就是 "Group Relative" 的含义。
```

**为什么 RL 特别适合工业推理**：工业推理的答案往往可以程序化验证（CPK 可以精确计算、Nelson 规则有明确定义、代码可以跑单元测试），这提供了高质量的自动奖励信号。不需要人工标注就能产生海量训练数据。

**方法**：GRPO（Group Relative Policy Optimization）+ 规则化奖励

**工业 RL 训练数据**（可验证答案的工业推理题）：

| 任务类型 | 数量 | 验证方式 |
|---------|-----|---------|
| SPC 异常判断 | 5K | 规则验证（Nelson 八条规则） |
| CPK 计算 | 3K | 数值精确匹配 |
| 工艺参数范围判断 | 5K | 专家规则库验证 |
| 工业数学推导 | 10K | 符号计算验证 |
| 工业代码生成 | 10K | 单元测试执行 |

**奖励设计**：
```python
reward = accuracy_reward + format_reward - length_penalty

accuracy_reward:
  - 数值精确匹配：+1.0
  - 范围正确：+0.5
  - 完全错误：0.0

format_reward:
  - 包含推理步骤：+0.2
  - 引用标准/规范：+0.1
  - 数值带单位：+0.1

length_penalty:
  - 超过 2000 tokens 无实质内容：-0.1
```

> RL 数据的核心要求：**答案必须可程序化验证**。`verify_type` 支持 `numerical`（数值精确匹配）、`rule`（规则命中检查）、`unit_test`（代码执行测试）、`symbolic`（符号计算验证）四种。

**参考 MiMo 的关键技术**（以 v2-pro 实际能力与训练经验为准）：
- **测试难度驱动的代码奖励**：对不同难度测试用例给予差异化奖励（细粒度奖励信号）
- **简单问题重采样**：提高 rollout 效率，稳定策略更新
- **上下文窗口逐步扩展**：从较短上下文逐步扩展到更长上下文（以 v2-pro 训练稳定性为准）

> 参考：MiMo 的 MTP、可验证题 RL、difficulty-driven code reward 与重采样等训练要点见论文。[^S5]

### 6.6 阶段五：多模态对齐（VLM 扩展）

**目标**：支持工业视觉场景（图像/视频/数据图表）

**训练原理——模型怎么"看"图片**：

语言模型只能处理文字（token 序列），无法直接处理图片像素。VLM 的解决方案是在语言模型前面加一个"翻译器"，把图片翻译成语言模型能理解的向量：

```
                    ┌──────────────┐
  工业图片          │  视觉编码器   │     ┌──────────┐     ┌──────────┐
  (像素矩阵)  ───→ │  (ViT)       │ ──→ │ 投影层    │ ──→ │          │
                    │ 将图片切成小块│     │ 将图片向量 │     │ 语言模型  │ ──→ "检测到焊点
                    │ 提取视觉特征  │     │ 映射到文字 │     │ (Qwen3)  │      桥接缺陷..."
                    └──────────────┘     │ 向量空间   │     │          │
                                         └──────────┘     └──────────┘
  用户提问                                                      ↑
  "这张 PCB 板有什么缺陷？" ─────────────────────────────────────┘
```

**三个组件**：
1. **视觉编码器（ViT）**：把图片切成 14×14 像素的小块（patch），每个小块提取一个特征向量。一张 448×448 的图片 → 1024 个视觉向量
2. **投影层（Projection）**：一个小型神经网络，把视觉向量从"图片空间"映射到"文字空间"，让语言模型能理解
3. **语言模型**：接收"图片向量 + 文字 token"的混合序列，像处理纯文字一样生成回答

**训练方式**：
- 视觉编码器通常**冻结**（不更新参数），复用已训练好的模型（如 Qwen2.5-VL 的 ViT）
- 投影层**从头训练**（参数量很小）
- 语言模型用 **LoRA 微调**（学会根据图片特征生成工业分析文本）
- 训练数据：工业图片 + 人工标注的分析文本（与 SFT 格式一致，只是 user 消息包含图片）

**基础方案**：基于 Qwen2.5-VL-72B 进行工业视觉微调

### 6.7 参数高效微调（PEFT）策略

**为什么不直接更新全部参数**：

一个 32B 模型有 320 亿个参数。全量微调需要在显存中同时放下：模型参数（~64GB）+ 梯度（~64GB）+ 优化器状态（~128GB）= **~256GB**，需要 4 张 H100。而且全量微调容易"过拟合"——在工业数据上训太狠会忘记通用能力。

LoRA 的核心思想是：**微调时不需要更新全部参数，只需更新一小部分"增量"参数。**

```
全量微调：直接修改模型的权重矩阵 W（巨大）

                W (32B 参数)
  输入 x ──→ [████████████████] ──→ 输出
              全部更新，显存巨大


LoRA：冻结原始 W，旁边加两个小矩阵 A 和 B（低秩分解）

                W (冻结，不更新)
  输入 x ──→ [████████████████] ──→ ┐
              ┌──────────────────┐    ├──→ 输出 = Wx + BAx
  输入 x ──→ │ B(小) × A(小)    │ ──→ ┘
              └──────────────────┘
              只更新 A 和 B，显存很小

  例：W 是 4096×4096 = 1600万参数
      A 是 4096×128 = 52万参数
      B 是 128×4096 = 52万参数
      → 只更新 104 万参数，是原来的 6%，显存需求大幅降低
```

**rank（秩）的含义**：A 和 B 的中间维度。rank=128 意味着用 128 维的"摘要"来近似原始的参数更新。rank 越大表达能力越强，但显存和计算也越多。

| 方法 | 原理 | 适用阶段 | 可训练参数占比 | 优势 | 局限 |
|------|------|---------|-------------|------|------|
| **LoRA** | 冻结原始权重，旁加低秩矩阵 A×B | SFT / CPT / DPO | 0.1–1% | 稳定、广泛验证，显存降 70%+ | rank 较低时表达能力受限 |
| **QLoRA** | 先把原始权重量化为 4-bit（节省存储），再加 LoRA | SFT / DPO（显存受限） | 0.1% | 32B 模型仅需 ~18GB/卡，4 卡可训 | 量化引入少量精度损失（~1-2%） |
| **DoRA** | 将 LoRA 改为"幅度+方向"分解，分别学习 | SFT / DPO | 0.3–1% | 收敛更快、效果比 LoRA 好 1-3% | 计算量略高于 LoRA |
| **LoRA+** | 对 A 和 B 矩阵使用不同学习率（B 的学习率更高） | SFT / DPO | 0.3–1% | 效果接近 DoRA，实现简单 | 需要调两个学习率 |
| **Full FT** | 直接更新全部参数 | RL（GRPO） | 100% | 表达能力最强 | 显存需求极高；仅在 RL 策略梯度更新阶段有不可替代优势 |

**推荐策略**：
- CPT 阶段：LoRA（rank=64）— 注入知识不需要太高的 rank
- SFT 阶段：LoRA（rank=128）或 DoRA — 对齐任务格式需要更强的表达能力
- DPO 阶段：LoRA（rank=64）— 偏好调整的参数变化较小
- RL 阶段：LoRA GRPO 可行（4 卡方案），但全量微调效果最好（需 8+ 卡）

| 工人接受度低 | 低 | UX 设计，渐进式引入 |

## 九、项目路线

> 本章聚焦**大模型后训练本身**的项目路线——每条路线是一个独立可落地的后训练项目，有明确的问题定义、技术方案和分阶段交付计划。与第七章的"实施路线图"（按时间维度的总体计划）互补，本章按**项目维度**组织。

### 路线一：大模型协同分工架构 + 小模型工具调用专项微调

**【问题诊断】** 工具调用（查数据、调接口）不需要复杂推理能力，但当前由通用大模型全量承接，导致：① 每次查询都经历完整推理链路，响应慢、成本高；② 通用大模型未针对工具调用专项优化，参数格式类错误率高；③ 7B 专项精调模型在工具执行任务上可超越通用大模型。

**【为什么选 Qwen2.5-7B + SFT+GRPO？】** Qwen2.5 系列在工具调用基准上表现领先同参数量模型；7B 规模可在单卡推理（vLLM 量化部署）；GRPO 在工具调用奖励建模上有 DeepSeek-R1 实践支撑，优于单纯 SFT。

**核心设计：按任务类型分工，而非全量替换**

```
mimo-v2-pro-imp（规划 + 复杂推理）         Qwen2.5-7B-FT（工具调用执行）
├ 理解用户意图，判断任务类型                 ├ 接收 mimo 分派的数据查询任务
├ 复杂推理任务（跨域分析、多维判断、         ├ 执行多轮工具调用（含依赖链推理）
│ 开放问答）：自主执行                       ├ 精准填写参数，处理先后依赖关系
├ 常规数据查询任务：委托 Qwen2.5-7B-FT      ├ 返回结构化查询结果给 mimo
│ 执行工具调用                               └ 不参与复杂推理与最终报告生成
└ 接收结构化查询结果，整合生成最终分析报告
```

```
用户请求
    ↓
mimo-v2-pro-imp（任务理解 + 类型判断）
    ├── 复杂推理任务 ──────────────→ mimo 自主执行 → 直接回答
    └── 常规数据查询任务 ↓
        Qwen2.5-7B-FT（多轮工具调用执行）← SFT+GRPO 专项微调
            ↓ 工具执行层（ontology_tools.py）
            ↓ 结构化查询结果返回
        mimo-v2-pro-imp（数据整合 + 最终报告生成）
            ↓
        用户
```

**训练策略：SFT + GRPO 两阶段**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：SFT** | 有监督微调 | 用真实生产工具调用对话做格式对齐；学会 6 个核心工具的调用语义、参数格式、多步依赖链；建立工具调用基础能力，降低格式错误率 | 10K–30K 条工具调用对话 |
| **第二阶段：GRPO** | 强化学习优化 | 基于 SFT 模型，以工具调用结果正确性为奖励信号；优化多步工具调用中的决策链，减少冗余调用和错误路径；对标 DeepSeek-R1 训练思路，增强模型自主推理能力 | 5K–10K 可验证工具调用题 |

**分阶段交付**：

```
Phase 1（0–6 周）：SFT 基础能力
  ├── 收集生产环境工具调用日志，构建 SFT 数据集
  ├── Qwen2.5-7B LoRA SFT（工具调用格式对齐）
  ├── 评测：工具调用格式正确率 >95%，单轮调用准确率 >90%
  └── 部署：与 mimo-v2-pro-imp 联调，A/B 测试

Phase 2（6–12 周）：GRPO 推理增强
  ├── 构建可验证工具调用题集（含多轮依赖链）
  ├── GRPO 训练（奖励 = 工具调用结果正确性）
  ├── 评测：多轮工具调用链成功率 >85%，冗余调用减少 >30%
  └── 全量上线，替代 mimo 直接工具调用

Phase 3（12–16 周）：持续优化
  ├── 线上工具调用失败案例自动回流
  ├── 增量 SFT + GRPO 迭代
  └── 目标：工具调用综合成功率 >95%
```

### 路线二：大模型 Skill 内化（隐私保护 + 商业化支撑）

**【问题诊断】** 当前每次推理将完整 Skill SOP 文档注入 user_content 发送至第三方 API，生产工艺、质量标准等商业敏感内容实时传输，带来三重问题：① 知识产权无法保护；② 无法满足客户数据合规要求；③ SOP 文本占用大量 context window，推高推理成本（约 30–50% token）。

**【为什么选"训练后删源"方案？】** 相比 RAG 检索方案，内化后推理时不传输任何 Skill 内容，安全性从"加密传输"升级为"物理不存在"；相比私有化部署（客户侧部署 API），内化方案不依赖客户基础设施，交付更简单。

**解决方案**：训练后删源选用更大参数量模型（Qwen2.5-32B 或 72B），在包含完整 Skill 内容的对话数据上做 SFT 微调，训练完成后**删除原始 Skill 文档**，推理时无需传入任何 Skill 内容，模型从权重中调用内化知识。

```
隐私保障                        商业化支撑                     成本优化
├ Skill SOP 固化进权重           ├ 专属 Skill 私有化封装        ├ Skill 文本不再占用 context window
├ 训练后删除原始文档             ├ 交付模型权重，知识不可        ├ 每次对话减少约 30–50% token 消耗
└ 推理时零明文传输               │ 逆向提取                    └ 同等资源下支撑更高并发
                                └ 客户无需部署额外基础设施
```

**训练策略：Skill 感知 SFT**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：Skill 数据构建** | 对话数据合成 | 将 Skill SOP 文档转换为多轮对话训练数据，覆盖知识点、边界条件、异常场景 | 每个 Skill 生成 500–2000 条对话 |
| **第二阶段：SFT 内化训练** | LoRA SFT | 在包含完整 Skill 上下文的对话上微调，模型学会在无 Skill 文本提示下直接回答 | 全量 Skill 对话数据 |
| **第三阶段：无源评测** | 评测验证 | 移除所有 Skill 文档，仅用模型权重推理，对比有/无 Skill 注入时的回答质量 | Skill 专项评测集 |
| **第四阶段：删源交付** | 交付 | 确认无源推理质量达标后，删除原始 Skill 文档，交付模型权重 | — |

**分阶段交付**：

```
Phase 1（0–4 周）：数据构建 + 内化验证
  ├── 选取 3–5 个典型 Skill 作为试点
  ├── 构建 Skill 对话数据（每 Skill 1000 条）
  ├── LoRA SFT 训练 + 无源评测
  └── 验证：无源推理 vs 有源推理质量差距 <5%

Phase 2（4–8 周）：全量内化
  ├── 扩展至全部 Skill（20–50 个）
  ├── 批量数据生成 + 统一训练
  ├── 全量无源评测通过
  └── 删源，交付内化模型

Phase 3（8–12 周）：商业化封装
  ├── 建立 Skill 内化自动化 Pipeline（新 Skill → 数据生成 → 训练 → 评测 → 交付）
  ├── 支持按客户定制（不同客户内化不同 Skill 子集）
  └── 建立内化质量监控体系（定期抽检内化知识衰减）
```

### 路线三：时序大模型微调（工况漂移识别）

**【问题诊断】** 工业设备异常检测面临三重约束：① 故障样本极少甚至为零，有监督方法无从训练；② 针对一台设备调好的模型换到另一台即失效，逐设备建模成本随设备数线性增长；③ 现有预训练时序大模型（iTransformer、PatchTST 等）在公开数据集上预训练，缺乏工业领域适配，直接使用效果有限。

**【为什么选"预训练时序大模型+LoRA+无监督"组合？】** 预训练大模型提供通用时序表征能力（解决小样本问题）；LoRA 微调用工业数据做领域适配（解决泛化不足）；无监督异常评分绕开故障标注依赖（解决标注难题）。三者缺一不可，组合才能覆盖三重约束。

**核心设计：预训练时序大模型 + LoRA 领域微调 + 无监督异常评分**

```
LoRA 参数高效微调                ArcFace 嵌入优化               无监督异常评分
├ 冻结预训练权重，仅训练低秩      ├ 用数据元信息（场景/传感器      ├ 仅用正常样本构建参考库，
│ 旁路参数（< 0.5%）            │ 方向）构造辅助分类目标         │ 无需任何故障标注
├ 防止小样本过拟合，保留通用      ├ 在角度空间收紧正常样本嵌入，    ├ 测试样本偏离参考库即判异常
│ 泛化能力                       │ 异常偏离即可检出               │ （kNN / Mahalanobis）
└ 显存需求从 ~8GB 降至 ~4GB      └ 训练完成后丢弃分类头，仅保留    └ 融合时域机理分析，提供可解释
                                   Encoder 提取特征               │ 的故障部位定位
```

**训练策略：LoRA + ArcFace + 异常评分 三阶段**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：LoRA 领域微调** | 冻结预训练时序模型 + LoRA（rank=16–32） | 用工业时序数据微调，学习设备振动/温度/压力的领域特征分布 | 正常运行数据 10K–100K 条时序片段 |
| **第二阶段：ArcFace 嵌入优化** | 辅助分类任务 + ArcFace Loss | 利用场景/传感器方向等元信息构造代理分类任务，收紧正常样本嵌入空间 | 同上 + 元信息标签 |
| **第三阶段：无监督异常评分部署** | kNN / Mahalanobis 距离 | 用正常样本嵌入构建参考库，在线推理时计算测试样本与参考库的距离，超阈值即报警 | 参考库：正常样本嵌入 |

**分阶段交付**：

```
Phase 1（0–6 周）：单设备验证
  ├── 选取 1–2 类典型设备（如注塑机、SMT 贴片机）
  ├── 收集正常运行时序数据（振动/温度/压力）
  ├── 预训练时序模型 + LoRA 微调 + ArcFace 嵌入
  ├── 构建正常参考库，部署无监督异常评分
  └── 评测：异常检测 AUC >0.90，误报率 <5%

Phase 2（6–12 周）：多设备泛化
  ├── 扩展至 5–10 类设备，验证跨设备泛化能力
  ├── LoRA 适配器按设备类型分组训练（共享预训练主干）
  ├── 融合时域机理分析，输出可解释故障部位
  └── 评测：新设备零样本 AUC >0.85，有少量校准数据 AUC >0.92

Phase 3（12–18 周）：产线级部署
  ├── 边缘部署（单卡 GPU / NPU，< 4GB 显存）
  ├── 与装备 Agent 集成（异常检测 → 自动触发诊断流程）
  ├── 持续学习：新设备上线时自动构建参考库
  └── 目标：覆盖工厂 80% 关键设备，异常检出率 >95%
```

### 路线四：Agent 轨迹自举训练（Rejection Sampling + 在线 RL）

**【问题诊断】** Agent 场景（装备 Agent、线长 Agent）的高质量训练数据极度稀缺——每条 Agent 轨迹包含多轮工具调用、条件分支、错误恢复，人工标注成本高（每条 30–60 分钟）且难以覆盖长尾场景。仅靠人工标注的 SFT 数据无法突破 Agent 任务完成率瓶颈。

**【为什么选"自举 + 在线 RL"？】** Rejection Sampling 让模型自己在仿真环境中执行任务，筛选成功轨迹作为新训练数据，突破人工标注瓶颈；在线 RL 进一步优化决策策略，减少冗余步骤。这是 OpenAI、Anthropic 等在 Agent 训练上的核心范式。

**核心设计：仿真环境 + 轨迹采样 + 自动筛选 + 迭代训练**

```
仿真环境（数字孪生工厂）              轨迹自举循环
├ 模拟 MES/ERP/SCADA 接口            ├ 当前模型在仿真环境中执行任务
├ 模拟设备传感器数据流                ├ 自动判定任务是否成功（结果验证）
├ 模拟异常注入（故障/物料短缺）       ├ 筛选成功轨迹 → 加入 SFT 数据集
└ 提供确定性评估（成功/失败/部分成功） ├ 用新数据集重新 SFT → 模型变强
                                      ├ 更强模型 → 采样更多成功轨迹
                                      └ 循环迭代直到收敛
```

**训练策略：三阶段自举**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：种子 SFT** | 人工标注 + 教师模型生成 | 用少量高质量轨迹（1K–5K 条）训练初始 Agent 模型 | 人工标注轨迹 |
| **第二阶段：Rejection Sampling 自举** | 模型自采样 + 成功筛选 | 在仿真环境中执行 10K–50K 次任务，筛选成功轨迹（~30% 成功率）→ 3K–15K 新 SFT 数据 | 自动生成 |
| **第三阶段：在线 RL** | GRPO + 任务完成奖励 | 在仿真环境中在线训练，奖励 = 任务完成度 + 步骤效率 + 安全合规 | 在线交互 |

**分阶段交付**：

```
Phase 1（0–8 周）：仿真环境 + 种子模型
  ├── 搭建数字孪生工厂仿真环境（至少覆盖装备 Agent 核心 10 类任务）
  ├── 人工标注种子轨迹 2K 条 + 教师模型生成 3K 条
  ├── 种子 SFT 训练，任务完成率基线 ~50%
  └── 仿真环境验证通过

Phase 2（8–14 周）：自举迭代
  ├── Rejection Sampling：模型执行 30K 次任务，筛选成功轨迹
  ├── 迭代 3–5 轮（每轮：SFT → 采样 → 筛选 → SFT）
  ├── 任务完成率从 ~50% 提升至 ~80%
  └── 同步扩展线长 Agent 仿真场景

Phase 3（14–20 周）：在线 RL + 真实环境验证
  ├── 在仿真环境中在线 GRPO 训练
  ├── 任务完成率从 ~80% 提升至 ~90%
  ├── 真实产线 A/B 测试验证
  └── 目标：Agent 任务完成率 >90%，人工干预率 <10%
```

### 路线五：工业安全对齐专项微调

**【问题诊断】** 工业场景的安全边界与通用对话截然不同：① 高危操作（调参/停机/加热）如果模型不拒绝或不提示确认，可能造成人身伤害或设备损坏；② 通用 RLHF 训练的安全策略过于保守（"我不确定"式拒答），不适合工厂现场需要明确指令的场景；③ 涉密信息（产品参数、良率数据、客户信息）需要精细化分级管控，而非一刀切拒绝。

**【为什么需要专项对齐？】** 通用模型的安全对齐面向网络安全/内容审核，工业安全对齐需要领域专有的安全分类体系（人身安全 > 设备安全 > 数据安全 > 合规）、分级响应机制（拒绝/警告/确认/放行）、以及安全与效率的平衡。

**核心设计：工业安全分级 + 红队测试 + 对齐训练**

```
安全分级体系                         对齐训练数据
├ S0 人身安全：绝对拒绝               ├ 安全拒绝样本（高危操作识别 + 拒绝话术）
│  （如：未停机进入机械臂工作范围）    ├ 安全确认样本（中危操作 + 二次确认流程）
├ S1 设备安全：强制确认               ├ 安全放行样本（正常操作 + 安全提示）
│  （如：调整回流焊温度超出 ±20°C）   ├ 涉密信息分级管控样本
├ S2 数据安全：权限校验               └ 红队对抗样本（绕过安全策略的攻击 + 正确应对）
│  （如：查询其他产线良率数据）
└ S3 合规安全：审计记录
   （如：工艺变更需工单审批）
```

**训练策略：安全数据构建 + DPO 对齐 + 红队迭代**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：安全分类数据构建** | 人工构造 + 规则生成 | 构建工业安全场景分类数据集，覆盖 S0–S3 各级 | 5K–10K 条安全场景对话 |
| **第二阶段：安全 DPO** | DPO 偏好优化 | chosen = 正确安全响应，rejected = 过度拒绝或安全遗漏 | 3K–5K 偏好对 |
| **第三阶段：红队测试 + 迭代** | 对抗测试 | 组织工程师模拟绕过安全策略的提问，收集失败案例，迭代训练 | 持续迭代 |

**分阶段交付**：

```
Phase 1（0–4 周）：安全体系建立
  ├── 定义工业安全分级标准（S0–S3）
  ├── 构建安全场景数据集（5K 条）
  ├── 安全 DPO 训练
  └── 评测：高危操作拒绝率 100%，正常操作误拒率 <3%

Phase 2（4–8 周）：红队对抗
  ├── 组织工厂工程师 + 安全团队红队测试
  ├── 收集绕过案例，构建对抗训练数据
  ├── 迭代 DPO 训练
  └── 评测：红队攻击成功率 <5%

Phase 3（8–12 周）：集成上线
  ├── 与装备 Agent / 线长 Agent 安全策略集成
  ├── 建立安全事件审计日志
  └── 持续红队迭代机制常态化
```

### 路线六：RAG 与微调协同优化（工厂问答增强）

**【问题诊断】** 工厂问答系统面临"知识时效性"与"推理深度"的双重需求：① 设备手册、SOP 文档频繁更新，纯微调模型无法实时同步最新知识；② 纯 RAG 方案检索召回率受限（工业文档表述多样、口语化严重），且模型对检索结果的理解和推理能力不足；③ 当前 RAG 和微调是独立优化的，未形成协同增效。

**【为什么需要协同优化？】** 微调让模型"懂工业语言"（提升检索结果理解力），RAG 让模型"知道最新知识"（补齐时效性）。两者协同可突破各自瓶颈：微调后的模型对 RAG 召回文档的理解更准确，RAG 反过来补齐微调数据中未覆盖的长尾知识。

**核心设计：微调增强检索理解 + RAG 补齐知识时效 + 联合优化**

```
微调侧                              RAG 侧                         联合优化
├ CPT 内化工业术语（提升              ├ 工业文档向量化                  ├ SFT 数据中混入 RAG 上下文
│ 检索 query 改写质量）              │ （设备手册/SOP/工单）           │ （教模型利用检索结果推理）
├ SFT 训练"引用检索结果               ├ 混合检索（语义+关键词+          ├ DPO：有引用 > 无引用 >
│ 回答"的能力                        │ 结构化字段）                   │ 错误引用
└ RL 训练引用准确性                   └ 定期增量索引更新               └ 端到端评测闭环
```

**训练策略：RAG-aware SFT + 引用 DPO**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：RAG-aware SFT** | 在 SFT 数据中注入检索上下文 | 教模型"读懂检索结果 + 正确引用 + 识别检索噪声" | 30K 条（含检索上下文的问答对） |
| **第二阶段：引用 DPO** | DPO 偏好优化 | chosen = 正确引用文档段落，rejected = 无引用/错误引用/幻觉引用 | 5K–10K 偏好对 |
| **第三阶段：检索质量 RL** | GRPO | 奖励 = 回答准确性 × 引用命中率，惩罚幻觉引用 | 5K 可验证问答 |

**分阶段交付**：

```
Phase 1（0–6 周）：RAG 基建 + RAG-aware SFT
  ├── 构建工业文档向量库（设备手册/SOP/工单/标准）
  ├── 实现混合检索（语义 + 关键词 + 结构化字段过滤）
  ├── 构建 RAG-aware SFT 数据（在训练对话中注入检索上下文）
  ├── LoRA SFT 训练
  └── 评测：引用准确率 >80%，首轮解决率比纯 RAG 提升 >15%

Phase 2（6–10 周）：引用 DPO + 检索优化
  ├── 构建引用偏好对（正确引用 vs 幻觉引用 vs 无引用）
  ├── DPO 训练
  ├── 检索 query 改写优化（利用微调模型做 query expansion）
  └── 评测：幻觉引用率 <5%，检索召回率提升 >10%

Phase 3（10–14 周）：端到端优化 + 上线
  ├── RL 训练（引用命中率作为奖励信号）
  ├── 增量索引自动化（新文档上传 → 自动向量化 → 自动测试）
  └── 目标：工厂问答满意度 >4.3/5，知识时效性 <24h
```

### 路线七：领域小模型蒸馏（端侧 / 边缘部署）

**【问题诊断】** 工厂现场部分场景需要超低延迟（<100ms）和离线可用：① 装备 Agent 在设备侧实时响应，不能依赖云端；② 部分工厂网络环境差或有气隙隔离，无法稳定访问云端大模型；③ 部署 32B 模型到每台设备旁成本不可接受，需要 1.5B–7B 级别的小模型。

**【为什么选蒸馏而非直接训小模型？】** 小模型直接在工业数据上训练，数据量不足以训出足够能力；通过大模型蒸馏，可以将 32B 模型的工业推理能力"压缩"到 1.5B–7B 模型中，小模型获得远超自身规模的领域能力。

**核心设计：教师模型生成 + 学生模型蒸馏 + 任务特化**

```
教师模型（32B，云端）                学生模型（1.5B–7B，边缘）
├ 工业后训练完成的 Qwen3-32B         ├ Qwen3-1.5B / Qwen3-7B 基座
├ 在全量工业任务上生成推理轨迹        ├ 在教师轨迹上 SFT 蒸馏
├ 包含 <think> 推理链                ├ 蒸馏后进行任务特化剪枝
└ 每个任务生成 N 条 → 筛选最优       └ 量化部署（INT4/INT8）
```

**训练策略：推理链蒸馏 + 任务特化 + 量化部署**

| 阶段 | 方法 | 目标 | 数据 |
|------|------|------|------|
| **第一阶段：教师轨迹生成** | 32B 模型批量推理 | 用教师模型在工业任务上生成高质量推理轨迹（含 CoT） | 50K–100K 条推理轨迹 |
| **第二阶段：学生蒸馏 SFT** | 知识蒸馏 + SFT | 在教师轨迹上训练学生模型，学习推理模式和领域知识 | 教师轨迹数据 |
| **第三阶段：任务特化 + 量化** | 按场景裁剪 + INT4 量化 | 针对具体边缘任务（如单一设备类型的异常检测）做特化微调，然后量化 | 场景特化数据 |

**分阶段交付**：

```
Phase 1（0–6 周）：蒸馏验证
  ├── 选取装备 Agent 核心 5 类任务
  ├── 教师模型生成 50K 推理轨迹
  ├── Qwen3-7B 蒸馏 SFT
  └── 评测：7B 蒸馏模型达到 32B 教师模型 85–90% 的工业任务准确率

Phase 2（6–10 周）：极致压缩
  ├── Qwen3-1.5B 蒸馏（面向单一任务特化）
  ├── INT4 量化（GPTQ / AWQ）
  ├── 边缘设备部署验证（Jetson / NPU / 工控机）
  └── 评测：1.5B-INT4 在特化任务上达到 32B 的 80%，延迟 <50ms

Phase 3（10–14 周）：产线部署
  ├── 与设备控制系统集成（OPC-UA / Modbus 接口）
  ├── 离线推理验证（无网络环境下稳定运行）
  └── 目标：覆盖 3–5 类设备的边缘 Agent 部署
```

### 路线总览对比

| 路线 | 核心后训练技术 | 解决的核心问题 | 基座模型 | GPU 需求 | 交付周期 |
|------|-------------|-------------|---------|---------|---------|
| **一：协同分工 + 工具调用微调** | SFT + GRPO | 工具调用成本高、格式错误率高 | Qwen2.5-7B | 2–4×H100 | 12–16 周 |
| **二：Skill 内化** | SFT（知识固化） | 知识产权泄露、推理成本高 | Qwen2.5-32B/72B | 4–8×H100 | 8–12 周 |
| **三：时序大模型微调** | LoRA + ArcFace + 无监督 | 故障样本稀缺、跨设备泛化差 | 预训练时序模型 | 1–2×H100 | 12–18 周 |
| **四：Agent 轨迹自举** | Rejection Sampling + GRPO | Agent 训练数据稀缺 | Qwen3-32B | 4–8×H100 | 14–20 周 |
| **五：工业安全对齐** | DPO + 红队迭代 | 工业安全策略缺失 | Qwen3-32B | 4×H100 | 8–12 周 |
| **六：RAG + 微调协同** | RAG-aware SFT + DPO | 知识时效 vs 推理深度矛盾 | Qwen3-32B | 4×H100 | 10–14 周 |
| **七：小模型蒸馏** | 知识蒸馏 + 量化 | 边缘部署成本与延迟 | Qwen3-1.5B/7B | 2–4×H100 | 10–14 周 |
