# 大模型训练数据指南

> 以智能制造领域为例
> 两个主题：微调数据 · 预训练数据

---

## 一、微调数据（Fine-tuning Data）

### 1.1 微调的起点与目标

```
预训练基础模型（已有语言能力）
        │
        ▼
   微调（Fine-tuning）
        │
        ├── SFT：学会特定技能（工具调用、规则判断、格式输出）
        └── RLHF/DPO：对齐偏好（答案风格、安全边界）
        │
        ▼
  领域专用模型（保留语言能力 + 获得领域技能）
```

**关键前提**：微调不从随机权重开始，始终基于已预训练的基础模型。

---

### 1.2 微调数据来源

```
智能制造微调数据
│
├── 系统生成（自动、持续）
│   ├── 生产执行日志（MES / SCADA / Langfuse）
│   ├── 告警与异常记录
│   └── 设备运行快照
│
├── 人工构造（主动、可控）
│   ├── 教师模型合成（Claude + skill doc → 推理链 + 答案）
│   └── 程序化场景生成（代码随机构造，覆盖边界条件）
│
├── 人机交互（历史沉淀）
│   ├── 已部署助手的历史会话
│   └── 帮助台 / 工单 / 飞书历史问答
│
└── 人工标注（小量高价值）
    ├── 边界案例专项标注
    └── 偏好对比标注（chosen / rejected）
```

---

### 1.3 各来源特征与适用场景

| 来源 | 获取成本 | 质量可控性 | 主要风险 | 适合任务 |
|------|---------|-----------|---------|---------|
| 生产日志 | 低 | 低（需验证） | 捷径污染、推理链缺失 | 工具调用、真实问法多样性 |
| 教师模型合成 | 中 | 高 | 问法模板化、偏离真实分布 | 需完整推理链的任意任务 |
| 程序化生成 | 低 | 高 | 边界覆盖依赖人工设计 | 规则判断、参数计算 |
| 历史对话 | 低 | 低（需过滤） | 低质量对话混入 | 意图理解、多轮对话 |
| 人工标注 | 高 | 最高 | 规模有限 | 边界案例、偏好对齐 |

---

### 1.4 质量提升流程

```
原始数据
   │
   ├─[过滤]─ 去除不完整轨迹、无最终答案、异常长度
   │
   ├─[验证]─ 参数来源验证（工作流类）
   │           每个工具参数 = 来自用户输入 或 前序工具返回
   │           不通过 → 重建或丢弃
   │
   ├─[去重]─ 语义去重，防止相似样本导致记忆化
   │
   ├─[多样性]─ 同类查询覆盖 ≥3 种参数变体
   │            防止模型记住单一值而非学会流程
   │
   └─[推理链]─ 验证 output 中 thinking block 完整性
               不完整 → 用 Claude 补全，再做 ns 转换
```

---

### 1.5 数据量与配比设计

| 场景 | 推荐数据量 | 配比建议 |
|------|-----------|---------|
| 新技能，无日志 | 200–500 条合成 | 技能数据 100% |
| 有日志，质量高 | 日志全量 + 合成补充多样性 | 日志 70% + 合成 30% |
| 有日志，捷径污染严重 | 重建 + 教师合成 | 视重建率决定 |
| 多技能混合 | 每技能 ≥ 100 条，总量 500–2000 | 技能均衡，加入 30% 通用数据防退化 |

**核心原则：数据质量 > 覆盖广度 > 数据数量。**

---

### 1.6 问题与讨论

**Q：生产日志和教师合成数据，应该以哪个为主？**

两者互补，不应只选一个。

生产日志的不可替代性：真实用户的问法千变万化（"今天 S04 的 UPH"、"04 线产出怎么样"、"昨天夜班那条线跑了多少"），这种多样性用模板生成很难覆盖。

教师合成的不可替代性：完整的推理链展开、明确的参数来源、可精准覆盖边界条件——这是日志往往缺失的。

实践建议：先用日志建立问法多样性，再用合成数据补全推理链质量和场景覆盖缺口。

---

**Q：数据不足时，先扩量还是先提质？**

几乎总应该先提质。Round 1/2 实验：去除 49 条截断样本（提质）的 F1 提升，超过新增 640 条低质量样本（扩量）。

例外：当某类样本在训练集中**完全缺失**（零覆盖），此时必须先扩量，因为质量再高也无法弥补覆盖空白。

---

**Q：微调会破坏模型的通用能力吗？如何缓解？**

会，这叫灾难性遗忘（catastrophic forgetting）。纯领域数据训练后，模型容易"只会说工厂话"，基础推理和格式能力退化。

缓解方式：在训练集中混入 20–30% 的通用指令数据（Alpaca/FLAN 类），用退化率（GSM8K 等基准测试的得分下降）量化影响并调整比例。LoRA 相比全量微调，遗忘程度更轻，因为基础权重被冻结。

## 二、预训练数据（Pre-training Data）

### 2.1 预训练的起点与目标

```
随机初始化权重
      │
      ▼
 预训练（Pre-training）
      │  目标：下一个 token 预测（无监督）
      │  数据：数万亿 token 的多样化文本
      │
      ▼
 基础模型（Base Model）
      │  具备语言理解、推理、知识储备
      │  但不会按指令行事
      │
      ▼
 （再经过 SFT / RLHF 才能对话使用）
```

**与微调的本质区别**：预训练从随机权重开始，目标是让模型"理解语言和世界"；微调在此基础上让模型"会做特定任务"。

---

### 2.2 预训练数据来源

```
通用语料（奠定语言与世界知识基础）
│
├── 网页文本（Common Crawl / C4）       ← 数量最大，质量参差
├── 书籍（Books3 / Gutenberg）           ← 质量高，长篇连贯推理
├── 学术论文（arXiv / PubMed）           ← 专业知识，逻辑严密
├── 代码（GitHub）                        ← 提升结构化推理能力
└── 多语言文本                            ← 中文比例影响中文能力

领域语料（强化智能制造知识）
│
├── 工业文档
│   ├── 设备手册、维修指南（结构化知识）
│   ├── 工艺规程、SOP（操作流程）
│   └── 质量标准（ISO/IEC/GB 等）
│
├── 行业数据
│   ├── 生产报表、班次日报（数值理解）
│   ├── 工单与缺陷记录（故障模式）
│   └── 传感器时序数据描述（物理过程）
│
└── 行业知识文本
    ├── 制造业技术论文、专利
    ├── 行业期刊（自动化、精益生产）
    └── 内部知识库、FAQ
```

---

### 2.3 数据规模参考

| 模型规模 | 典型预训练 token 数 | 智能制造领域语料估计 |
|---------|-------------------|-------------------|
| 1–3B | 500B–1T tokens | 数十亿 token |
| 7–14B | 1T–3T tokens | 数百亿 token |
| 70B+ | 3T–15T tokens | 千亿级 token |

> 智能制造领域语料通常占总量的 1–5%，比例过高会损失通用能力。

---

### 2.4 预训练数据质量提升

```
原始语料
   │
   ├─[规则过滤]─ 去除乱码、极短/极长文本、重复内容
   │              语言识别（非目标语言过滤）
   │              色情/暴力/有害内容过滤
   │
   ├─[质量分级]─ 启发式规则打分（标点比例、词汇丰富度、文本长度）
   │              分类器打分（用高质量文本训练的质量分类器）
   │              仅保留高分文本
   │
   ├─[去重]─────  文档级去重（MinHash LSH）
   │              句子级去重（极高频句子有害）
   │              ← 去重是最重要的单项质量操作
   │
   ├─[数据配比]─  通用 : 领域 ≈ 95:5 到 80:20
   │              代码比例影响推理能力，通常 5–15%
   │              多轮上采样高质量来源（书籍、论文）
   │
   └─[格式处理]─  HTML 清洗（去标签、保留结构）
                  表格/代码特殊处理（保留格式信息）
```

---

### 2.5 智能制造领域语料的特殊处理

| 数据类型 | 挑战 | 处理方式 |
|---------|------|---------|
| 设备手册（PDF） | 表格/图片信息丢失 | OCR + 表格结构化提取，图片转描述文本 |
| 传感器时序数据 | 模型不擅长处理原始数值序列 | 转换为自然语言描述（"温度从 23℃ 升至 67℃，历时 12 分钟"） |
| 工艺参数表 | 上下文依赖强 | 附加上下文（工序名称、设备型号）一起入库 |
| 内部术语 / 缩写 | 与通用语料含义不同 | 构建术语表，在数据中插入定义说明 |
| 多语言混合文档（中/英/德） | 语言切换混乱 | 按语言分离，或保留原始混合格式 |

### 2.6 问题与讨论

**Q：企业应该自己做预训练，还是基于开源模型微调？**

对绝大多数企业：**基于开源模型微调**，不要预训练。

预训练的实际门槛：14B 模型预训练需要数千 GPU 天、万亿级 token 语料，基础设施投入在千万级。Qwen、LLaMA 等开源模型已经包含了足够丰富的通用知识和语言能力。

例外情形：企业拥有大量独有领域数据（亿级 token 以上），且这些数据语言或知识形态与通用语料差异极大（如专有编程语言、内部业务系统文档）；此时可考虑"继续预训练"（Continue Pre-training），在已有开源模型基础上用领域语料继续训练，而非从随机权重开始。

---

**Q：继续预训练（Continue Pre-training）和 SFT 有什么区别？什么时候用？**

| | 继续预训练 | SFT |
|--|--|--|
| 训练目标 | 下一个 token 预测（无监督）| 指令-输出对（有监督）|
| 数据形式 | 大量无标注领域文本 | 有标注的问答/任务对 |
| 训练量 | 数十亿 token | 数百到数万条样本 |
| 目的 | 注入领域知识到权重 | 让模型会做特定任务 |
| 适用场景 | 模型对领域术语/概念完全不了解 | 模型有基础能力，需要学会特定行为 |

对智能制造：设备故障代码、工艺术语、专有系统命名等，通用模型通常已经了解一些。**如果模型能理解你的领域术语，直接 SFT 即可**；如果模型对关键术语一无所知，先做继续预训练，再做 SFT。

---

**Q：预训练数据中，代码的比例为什么会影响推理能力？**

代码是一种高度结构化、逻辑严密的语言，具有明确的因果关系（if → then）、层次结构（函数调用）和约束（语法规则）。大量实验表明，训练语料中加入代码能提升模型在数学推理、逻辑推理、结构化输出等任务上的能力，即使这些任务本身不涉及代码。

对智能制造：PLC 梯形图逻辑、SQL 查询语句、Python 数据分析脚本都是有价值的代码语料，在预训练中加入这些内容，可以间接提升模型对工厂系统调用逻辑的理解能力。
